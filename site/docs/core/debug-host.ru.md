# DebugHost

`DebugHost` принимает команды для работающего ядра. Координатор устанавливает его после инициализации игры. Транспорт передаёт JSON-запрос через `DebugHost.ExecuteAsync`, а хост выполняет команды последовательно на потоке Godot, в том числе при остановленном на паузе дереве. Отдельный адаптер MCP использует тот же диспетчер.

## Подключение к каналу ядра

Флаг `--development-control` после разделителя `--` в команде Godot или поле `development_control` в `config/mod_config.json` включает локальный именованный канал для того же пользователя. `--no-development-control` имеет приоритет и блокирует внешние подключения отладчика для этого запуска. У каждого процесса свой канал. Для публикации файла обнаружения укажите путь в `development_discovery`, например `user://dev_host.json`. Запрос из исходного дерева отправляет `DebugClient/dev_control.py`.

```shell
godot --path . -- --development-control
# Во втором терминале на той же системе и под тем же пользователем подставьте PID игры вместо 12345.
python DebugClient/dev_control.py 12345 '{"command":"args.catalog","key":"game"}'
```

## Команды ядра

| Команды | Назначение |
|---|---|
| `status`, `commands`, `describe` | Получить состояние процесса, список зарегистрированных команд и их описания |
| `diagnose`, `errors.pull` | Прочитать диагностику запуска и компиляции. Для следующей страницы `errors.pull` передайте `next` как `since` |
| `inspect` | Изучить узлы, ресурсы, кеши и зарегистрированные данные игры. Параметры фильтрации выдаёт `describe` |
| `node.inspect`, `node.set`, `node.tween`, `node.sine`, `node.motion.stop` | Найти, изменить или анимировать свойства живого узла |
| `args.read`, `args.catalog`, `args.set` | Прочитать или изменить [действующие аргументы запуска](launch-arguments.md) |
| `memory.stats`, `memory.inspect` | Прочитать [метрики и предпросмотр зарегистрированных хранилищ](memory.md) |
| `settings.read`, `settings.apply`, `settings.restore` | Прочитать или изменить [настройки экрана](display-settings.md) |
| `scene.switch`, `assets.refresh`, `mod.attach`, `mod.reload` | Запросить переход к логической сцене, обновление ресурсов или перезагрузку для разработки |
| `operation.status` | Узнать состояние операции по `operation_id` |

Для команды изменения передавайте UUID в `operation_id`. После обрыва соединения проверьте результат через `operation.status` с тем же UUID, прежде чем повторять запрос. Хост хранит ограниченную историю в текущем процессе.

### Управление узлами сцены

Найдите путь через `inspect` с `area=node` и фильтром `query` или `type`. Передайте этот путь в `node.inspect` с `list_properties=true`, чтобы получить имена и типы свойств Godot. Команды движения принимают `path` и `property`. Координаты 3D-векторов передаются массивом `[x, y, z]`.

| Команда | Пример параметров |
|---|---|
| `node.set` | `property="scale"`, `value=[1.5,1.5,1.5]` |
| `node.tween` | `property="rotation_degrees"`, `value=[-15,40,0]`, `duration_s=6` |
| `node.sine` | `property="position"`, `amplitude=[0,0.2,0]`, `period_s=4` |
| `node.motion.stop` | `property="position"` |

Новая анимация свойства заменяет предыдущую. Синус колеблется вокруг текущего значения, а `node.motion.stop` оставляет свойство в достигнутой точке. Анимация живёт до удаления узла. После плавного перехода проверьте итоговое значение через `node.inspect`. Если штатный контроллер сам пишет в свойство каждый кадр, используйте узел или камеру, подготовленные для ручного управления.

В 3D-локации с включённым режимом разработки **F7** включает свободную камеру. Мышь поворачивает обзор, **WASD** двигает камеру, **пробел/Ctrl** меняют высоту, **Shift** ускоряет полёт. Удерживайте **Alt**, чтобы освободить курсор. Повторная **F7** или **Esc** возвращает прежнюю камеру.

## Как ускорять эксперименты в одном процессе

Запустите оконную игру один раз. Затем через DebugHost меняйте параметры, пересоздавайте состояние сценария и повторяйте замер в том же Godot. Так загрузка процесса, ядра и модов выполняется один раз на серию. Подготовка новой карты и прогрев каждого сценария по-прежнему занимают время. Если измеряете сам холодный запуск, нужен отдельный процесс для каждого образца.

1. Запустите нужную игру или точечный тест. На Windows из `/workspace` запускайте игру и локальный клиент через action моста `hostserver` по `/workspace/hostserver/README.md`. `hostserver` доставляет PowerShell на Windows, а DebugHost внутри Godot принимает игровые команды. Адресуйте клиенту PID Godot из TestRunner, списка процессов или строки `debug host ready` в журнале. PID `dotnet` принадлежит TestRunner.
2. Дождитесь ответа `status`, проверьте `pid`, `instance`, игру и сцену, затем найдите команды через `commands` или `describe`. Кратковременное отсутствие канала во время старта ожидаемо. `dev_control.py --connect-timeout 45` ждёт открытия канала до 45 секунд. Когда он сообщает `command not sent`, подключение не состоялось. Если связь оборвалась после отправки изменения, проверяйте `operation.status` с исходным UUID. Для проверки окна дополнительно снимайте ID сессии Windows, HWND, видимость, свёрнутость и положение на мониторе.
3. Зафиксируйте исходное состояние и способ его восстановления. Держите одинаковыми seed, маршрут, состав бойцов, настройки графики, окно прогрева и длительность измерения. Меняйте один фактор или явно объявленную комбинацию. Повторите исходный вариант в конце серии, чтобы увидеть влияние прогрева процесса.
4. Сохраняйте для каждого варианта отдельный отчёт, включая PID, ID сцены, параметры и проверки результата. Для долгого сценария команда быстро возвращает подтверждение постановки, а драйвер продолжает работу между кадрами. Делайте запуск и опрос отдельными короткими action-заданиями, чтобы очередь Windows оставалась доступна для диагностики. Оценивайте результат по итоговому отчёту, артефактам и подтверждённому завершению, если сценарий закрывает процесс.

### Настройки и повторный замер

Следующий пример работает из корня проекта в PowerShell той же системы и пользователя, где запущен Godot. Подставьте текущий PID. Для команд `perf.*` заранее включите `perf_overlay`, например через `--with-mods=perf_overlay` в пользовательских аргументах игры. Перед `perf.read` дайте сцене отработать одинаковый интервал на каждом варианте.

```powershell
$gamePid = 12345
py -3 -B DebugClient/dev_control.py --pid $gamePid --connect-timeout 45 status

$start = @{ provider = 'perf_overlay'; command = 'perf.configure'; enabled = $true; overlay = $false; reset = $true; operation_id = [guid]::NewGuid().ToString() }
$start | ConvertTo-Json -Compress | py -3 -B DebugClient/dev_control.py $gamePid '-'
# Воспроизведите тот же маршрут и дождитесь окончания окна измерения.
'{"provider":"perf_overlay","command":"perf.read"}' | py -3 -B DebugClient/dev_control.py $gamePid '-'
```

Для A/B настроек прочитайте `settings.read`, отправьте `settings.apply`, запишите `result.restore_id` и запустите новое окно `perf.configure` с `reset=true`. После замера верните исходные значения командой `settings.restore` с этим `restore_id`. Для временного эксперимента оставьте `persist` выключенным. `scene.switch` и `mod.reload` подходят, когда сценарий требует смены сцены или обновления мода. У каждой команды свои предусловия, которые можно прочитать через `describe`.

### Ограничение ожидания на Windows

`--connect-timeout` у `dev_control.py` задаёт срок ожидания подключения. Для короткой диагностики, где важен также срок ответа, мы использовали `NamedPipeClientStream` в PowerShell. В этом примере есть отдельные пределы для подключения и ответа. Команда `status` только читает состояние.

```powershell
$gamePid = 12345
$pipe = [IO.Pipes.NamedPipeClientStream]::new('.', "cthangover-dev-$gamePid", [IO.Pipes.PipeDirection]::InOut)
try {
    $pipe.Connect(2000)
    $utf8 = [Text.UTF8Encoding]::new($false)
    $writer = [IO.StreamWriter]::new($pipe, $utf8, 1024, $true)
    $reader = [IO.StreamReader]::new($pipe, $utf8, $false, 1024, $true)
    try {
        $writer.WriteLine('{"command":"status"}')
        $writer.Flush()
        $reply = $reader.ReadLineAsync()
        if (!$reply.Wait(3000)) { throw 'DebugHost response timeout' }
        $reply.GetAwaiter().GetResult() | ConvertFrom-Json
    }
    finally {
        $reader.Dispose()
        $writer.Dispose()
    }
}
finally { $pipe.Dispose() }
```

Если требуется изменить состояние, сохраните UUID до отправки. Таймаут ответа не отменяет уже принятое изменение. Сверьте `operation.status` и журнал текущего PID. Если канал открылся, а `status` так и не ответил, снимите состояние процесса и окна средствами Windows.

### Реальный пример с боем Огнищанина

В эксперименте с коллизиями на поле мы сначала перезапускали Godot для каждого варианта. Затем открыли DebugHost в выделенном оконном запуске TestRunner для `ognishchanin_battle_field` и передали семь сценариев одним запросом в уже запущенный Godot. Канал Windows назывался `cthangover-dev-28608`. Первый опрос пришёл до открытия канала. После проверки PID повторное подключение через `NamedPipeClientStream` сработало без перезапуска игры. Протокол канала использует JSON по одной строке в UTF-8.

Для повторения примера нужен проверенный контекст TestRunner, набор `--itest=ognishchanin_battle_profile` и переменная `CTHANGOVER_BATTLE_DEBUG_MATRIX=1`, унаследованная Godot. В том запуске мы передали `--development-control` в пользовательские аргументы Godot через отдельную временную копию TestRunner. Это флаг игры. Стабильный `--input-cache` позволял переиспользовать подготовленные входы. Когда нужен фиксированный логический шаг, нативный `--fixed-fps 60` передаётся до `--`. Для диагностики обычной отрисовки мы его убрали.

```powershell
$gamePid = 12345  # PID того же Godot из ответа status
$provider = 'ognishchanin_game__battle_profile'
py -3 -B DebugClient/dev_control.py --pid $gamePid commands --mod $provider
@{ provider = $provider; command = 'battle.status' } |
    ConvertTo-Json -Compress | py -3 -B DebugClient/dev_control.py $gamePid '-'

$operation = [guid]::NewGuid().ToString()
@{
    provider = $provider
    command = 'battle.profile'
    modes = @('baseline', 'filter', 'support', 'late', 'filtered-support', 'combined', 'baseline')
    operation_id = $operation
} | ConvertTo-Json -Compress | py -3 -B DebugClient/dev_control.py $gamePid '-'
# Если ответ потерялся, проверьте существующую команду по её ID.
@{ command = 'operation.status'; operation_id = $operation } |
    ConvertTo-Json -Compress | py -3 -B DebugClient/dev_control.py $gamePid '-'
```

Ответ `result.scheduled = 7` подтвердил запуск первой серии. Драйвер выставляет режим контроллера до каждого сценария, вызывает штатный `GameSession.StartNew` и проверяет смену боевого состояния. Затем он ждёт новый `Scene3dHost`, готовую карту и четыре исходных бойца и разворачивает эталонный бой с 50 противниками и фиксированным seed. Результаты проверяйте по `process_id`, различным `scene_host_id`, обычным замерам в `frames.json` и итоговому `matrix.json`. Успешный кейс также требует двустороннего урона. `operation.status` возвращает результат команды постановки, состояние самих сценариев видно по журналу и артефактам.

Первая серия подтвердила, что можно повторно запускать сценарии в одном PID. Для сравнения коллизий её отбросили. Часть кейсов остановилась на стартовом ударе. Он проходил через вход пользовательского управления, где проверяется фокус окна. В тестовом драйвере скриптовый удар перевели на `Simulation.TryAction` с теми же боевыми проверками. Подозрение на зависшее окно проверили отдельным запуском без боя.

### Диагностика окна, загрузки и рендера

Снимите `status` и два `battle.status` с интервалом 2–3 секунды на одном PID. `battle.status` показывает `world_ready`, `world_progress`, `world_error`, `graphics_apply`, фокус, блокировку ввода и паузу, `process_frames`, `drawn_frames`, `physics_frames` и `combat_tick`. Сверьте эти показания с Windows. В отдельной проверке HWND присутствовал на активной сессии Windows и пересекал монитор, окно отвечало и оставалось в фоне. За время загрузки карта прошла с 3% до 100% примерно за 50 секунд. После готовности за три секунды появились 309 отрисованных кадров и 185 тиков физики. Пропажу окна из первого запуска повторить не удалось.

| Что меняется между снимками | Что проверять |
|---|---|
| Кадры растут, карта ещё загружается | Прогресс, ожидание `graphics_apply`, ошибки и блокировку ввода на время подготовки |
| Тики растут, отрисованные кадры стоят | Состояние окна, свёрнутость, рендер и GPU |
| Отрисованные кадры растут, видимого изображения нет | Показ кадров Windows по PID через [PresentMon](https://github.com/GameTechDev/PresentMon). Счётчики Godot измеряют отрисовку в движке |
| DebugHost перестал отвечать | Жив ли нужный PID, отвечает ли HWND, меняется ли CPU и что записано в нативном журнале. Диспетчер отладки сам зависит от потока Godot |

Перед включением результата в сравнение подтвердите окно, готовую карту и живые кадры. В том эксперименте окно `dotnet` принадлежало обвязке TestRunner. В повторной проверке консоль TestRunner запускалась скрытой, а окно Godot проверялось отдельно. Для одиночной оконной проверки `battle.finish-render-probe` завершает выделенный тестовый экземпляр после загрузки. Она требует `CTHANGOVER_BATTLE_RENDER_PROBE=1` и отдельного контракта результата `ognishchanin_battle_render_probe`, без зачёта боевого профиля.

## Одноразовые скрипты C#

Для `script.run` флаг `--allow-debug-scripts` должен быть и в исходных, и в действующих аргументах. `--no-development-control` блокирует команду. Передайте класс, реализующий `IDebugRuntimeScript`, в `source`, размером до 32 КиБ. `timeout_ms` принимает значения от 100 до 30 000 мс, по умолчанию 5000 мс. Поле `mods` позволяет указать идентификаторы активных сборок для ссылок при компиляции. В ответ входят JSON-результат, диагностика компилятора и статус выгрузки временного контекста. Скрипт выполняется с правами игрового процесса и отменяется кооперативно. Блокирующий вызов может занять поток Godot дольше таймаута. Выполняйте доверенный код, который проверяет токен отмены.
