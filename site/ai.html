Kernel and game cores

cthangover is not tied to a single genre. The C# kernel (Core/) provides genre-neutral infrastructure only: scenes and scenarios with the DSL, the mod registry, saves, resources, UI hosting, events, audio, and pluggable battle rulesets. It makes no assumptions about dialogue, portraits, or the shape of the game.

A game core is an ordinary mod that turns the kernel into a concrete game. visual_novel_core is the reference core shipped with the project: it defines characters, avatars, backgrounds, quests, items, and scenarios for a dialogue-driven story game. It is only one possible core — the kernel does not require it, and it uses the same public interfaces available to every mod.

Any genre can be built the same way. For example, a 2D sprite RPG with tile movement, turn-based encounters, and its own inventory UI can be plugged in as a core mod: it reuses the kernel (scenes, saves, events, resource pipeline) and brings its own assets, scenarios, actions, and UI scenes. The same approach works for other genres.

LayerLocationResponsibility
KernelCore/Genre-neutral services: scenes, scenario DSL, mods, saves, events, resources, UI, audio
Game coremods/<core>Defines a concrete game: content, rules, scenes, actions, UI
Gameplay modsmods/<mod>Extend a core or the kernel: patches, assets, custom actions, battle rulesets

A core can be disabled or replaced. Mods that depend on a specific core must declare it in depends — see Configs — manifest.json. The kernel itself never depends on a core.

Avatars

Source: docs/mods/avatars/index.md - https://cthangover.ru/docs/mods/avatars/index

Character portrait images displayed during dialogue scenes, positioned via first= (left, player) and second= (right, NPC) parameters.

Directory structure

avatars/
└── {character_name}/
    └── {expression}.png

Real example — Murakami

From mods/murakami/avatars/murakami/:

murakami/
├── normal_1.png      # neutral expression
├── normal_2.png      # neutral variant
├── fear_1.png        # scared
└── fear_2.png        # terrified

The compile-time catalog (Avatars.cs) additionally lists murakami/normal_3. Expressions are referenced as <character>/<expression> without the .png extension in DSL parameters (first= / second=).

Usage in scenarios

Avatars appear in dialogue lines through the text command:

text "- Help me..." key=murakami/help second=murakami/fear_1
text "- What are you doing here alone?" key=murakami/alone first=marao/think
  • first= — left-side speaker (usually the player)
  • second= — right-side speaker (usually the NPC)
  • The value is {character}/{expression} — no .png extension

Adding a new avatar set

  1. Create avatars/{character_name}/ in your mod
  2. Add .png files for each expression you need
  3. The character's JSON definition sets "Image" to the base path:
{
  "Id": "Murakami",                                        // Unique character identifier
  "Image": "characters/player/murakami"                    // Base path to character textures
}
  1. Use in scenarios: first=murakami/normal_1 or second=murakami/fear_1

Multiple characters in dialogue

The same expression naming convention works for any character:

avatars/
├── marao/
│   ├── sad.png
│   ├── smile.png
│   └── think.png
└── murakami/
    ├── normal_1.png
    ├── normal_2.png
    ├── fear_1.png
    └── fear_2.png

Note that the on-disk set and the compile-time catalog may differ slightly: Avatars.cs lists additional marao expressions (angry, what, relax) and a murakami normal_3, while marao's sad exists only as a file. Always check the mod's avatar directory for what is actually available.

Format requirements

  • Format: PNG with transparency
  • Resolution: 512×512 recommended, but any square power-of-two works
  • Naming: lowercase, underscores for multi-word expressions (fear_1, very_happy)
  • The extension is omitted in scenario files — the engine resolves {character}/{expression} to avatars/{character}/{expression}.png

Backgrounds

Source: docs/mods/backgrounds/index.md - https://cthangover.ru/docs/mods/backgrounds/index

Scene background images with optional depth maps for parallax effects and dynamic lighting.

Directory structure

backgrounds/
└── {scene_name}/
    ├── {image_name}.png
    └── {image_name}_depth.png   # optional depth map

Real example — Murakami meeting

From mods/murakami/backgrounds/town/meetingmurakami/:

meetingmurakami/
├── 00002-1920617752.png       # wolf tracks at the door
├── 00002-1920617752_depth.png # depth map for lighting
├── 00014-1724512349.png       # Murakami at her door
├── 00079-2783395178.png       # inside the house
├── 00078-2783395178.png       # inside, different angle
├── 00136-3647329618.png       # dark room
├── 00031-3535505844.png       # werewolf reveal
└── 00031-3535505844_depth.png

Each background has a matching _depth.png — a grayscale image where brightness encodes the Z-depth of each pixel. The light_set command uses it to cast dynamic shadows.

Usage in scenarios

background "town/meetingmurakami/00002-1920617752"
text "[Wolf tracks lead straight to the doorstep]" key=meeting/after_wolf/tracks

background "town/meetingmurakami/00014-1724512349"
text "- Dear lady!" key=meeting/after_wolf/greeting first=marao/think

The path is relative to backgrounds/ — no .png extension needed.

Scene default background

Each scene definition can specify a default background that loads when entering the scene:

{
  "name": "home_kitchen",                                  // Scene identifier
  "defaultBackground": "home/kitchen",                     // Background image loaded when entering the scene
  "defaultScenario": "scenarios/home/home_kitchen_default.scenario" // Default scenario to run on scene enter
}

Mods override backgrounds by setting a higher priority in their .scenario file.

Adding a new background

  1. Create backgrounds/{scene}/{name}.png in your mod
  2. Optionally create a {name}_depth.png grayscale depth map
  3. Reference in scenario: background "scene/name"
  4. If you want it as the default, update the scene JSON's defaultBackground

AI-generated backgrounds workflow

The project uses AI-generated (Stable Diffusion / Flux) images for backgrounds. Typical workflow:

  1. Generate a scene description prompt
  2. Get the base PNG
  3. Generate a depth map variant using a depth estimator or ControlNet
  4. Place both files in the appropriate folder

Battle System

Source: docs/mods/battle/index.md - https://cthangover.ru/docs/mods/battle/index

The battle engine is a pluggable, mod-driven system. Each battle ruleset is implemented as a mod (e.g. card_battle, ff_battle) following the IBattleCore interface. Battles are initiated from scenario scripts via action battle.init.

Architecture overview

Key interfaces

IBattleCore — Combat ruleset

Every battle system mod defines a class implementing IBattleCore:

MemberDescription
IdUnique string ID used by battle.set_core
ActionProviderReturns IActionExecutorProvider for overriding action executors
Init(Character[] playerChars, Character[] enemyChars, IBattleContext ctx)Called when battle starts — sets up UI, spawns enemies
Start()Called after Init — begins the battle loop

IActionExecutor — Ability resolution

Each battle action type (attack, defence, stun, item, etc.) has an executor:

MemberDescription
ActionIdUnique action identifier
Execute(action, user, target)Resolves the action against target

Executors are registered through ActionExecutorHub, which routes actions by ID at runtime.

GDScript mods can register executors as well — a .gd file with get_action_id() + execute(action, user, target) is auto-registered into the global executor registry. See GDScript in Mods for the full API.

IBattleContext — Engine bridge

Bridge from the battle core back to the engine so cores stay engine-agnostic:

MemberDescription
ApplyDamage(source, target, rawDamage, defence)Applies max(0, rawDamage - defence) to the target's Health directly (no event — the UI layer polls)
ScheduleAnimation(IBattleAnimation)Schedules visual feedback for playback
EndTurn(BattleSide side)Phase signal: the given side ends its turn
EndBattle(BattleSide winner)Ends the battle with the given winner
RootNodeGodot Node anchor for instantiating nodes (e.g. damage numbers)

Battle initialization flow

  1. Scenario runs action battle.set_core core=card_battle — selects the ruleset by ID. The registry is a case-sensitive dictionary and throws on an unknown ID; built-in IDs are card_battle and ff_battle
  2. Scenario runs action battle.init scene=... enemies=... quest_id=... new_tag=...
  3. BattleInitAction reads dialog variables, calls BattleService.Init()
  4. BattleData captures the current background
  5. BattleData.InitBattle resolves enemy character IDs to Character instances via CharacterFactory; unknown IDs get a fallback template character (20 HP, 3 action points)
  6. Active IBattleCore.Init() is called — mod sets up its UI panels
  7. IBattleCore.Start() begins the battle loop

Important: battle.init must run after the background has been set in the scenario, otherwise the battle gets a null backdrop.

Status effects

Status effects (buff, debuff, stun) are applied during battle via the StatusEffectQueue on each character. Effects have a duration in turns and expire automatically.

See Status Effects for the JSON definition format.

Victory screen listeners (winground)

The victory screen (Winground.tscn, driven by WingroundBehaviour) exposes an extension point for mods that want to modify EXP awards, alter generated loot, or run logic right before the UI appears. Implement IWingroundListener (Core/Battle/IWingroundListener.cs):

MemberDescription
IdUnique identifier (convention: "mod_id.listener_name"), used in logs and dependency ordering
OnBeforeExpAward(WingroundContext)EXP data is populated but not yet applied to characters; the loot list is still empty
OnAfterLootGenerated(WingroundContext)Loot has been rolled from defeated enemies but not yet added to inventory — mutate freely
OnBeforeShow(WingroundContext)All processing done; final chance to mutate data before the victory UI is shown

Hooks fire in that order during WingroundBehaviour.Show. The same WingroundContext instance is passed through every phase, so mutations made by earlier hooks are visible to later hooks and listeners.

Registration goes through the WingroundListenerRegistry singleton:

  • C# mods: implement IWingroundListener with a parameterless constructor — ModAssemblyLoader calls WingroundListenerRegistry.Instance.RegisterAssembly(assembly), which discovers and instantiates implementations automatically
  • Exceptions thrown by individual listeners are logged and swallowed so one broken mod cannot break the victory screen for others

WingroundContext

Mutable context shared by all listeners (Core/Battle/WingroundContext.cs):

FieldTypeDescription
PlayerExpGainedDictionary<string, int>Per-character EXP earned, keyed by character ID
DefeatedEnemiesList<Character>Enemies defeated this battle; drives loot generation and recruitment rolls
GeneratedLootList<ItemContainer>Loot items — add, remove, or modify entries before they are committed to inventory
BattleDataBattleDataReference to the battle descriptor shared with the quest system — do not mutate the object itself

GDScript variant

A .gd script exposing get_winground_listener_id() returning a unique string, plus any of the optional hooks on_winground_before_exp(ctx) / on_winground_after_loot(ctx) / on_winground_before_show(ctx), is detected by method signature in ModGDScriptLoader, wrapped in a GDWingroundListener, and registered automatically. All three hooks are optional — only the methods the script actually implements are called.

The C# context is marshalled into a GDWingroundContext (RefCounted) before each call and synced back afterwards: mutations to ExpGained and GeneratedLoot propagate to the C# victory pipeline, while DefeatedEnemies are exposed as read-only GDCharacter DTO snapshots whose changes are not written back.

extends RefCounted

func get_winground_listener_id() -> String:
    return "my_mod.double_exp"

func on_winground_before_exp(ctx) -> void:
    for id in ctx.ExpGained:
        ctx.ExpGained[id] *= 2

Battle speed control

BattleSpeedControl (Core/Battle/BattleSpeedControl.cs) is the x1/x4/x8 toggle bar shown during battle:

MemberDescription
ApplySavedSpeed()Restores Engine.TimeScale from GameData.Settings.BattleSpeed (out-of-range values fall back to x1); called automatically on _Ready()
ResetToNormal()Resets Engine.TimeScale to 1.0 without saving — used when the battle ends so menus run at normal speed

Picking a speed sets Engine.TimeScale, which accelerates the entire game loop (not just animations), and persists the choice to GameData.Settings.BattleSpeed.

Animation layer

Visual feedback is decoupled from combat logic so battle cores stay engine-agnostic (Core/Battle/Adapters/):

TypeRole
IBattleAnimationData-only description: Source/Target characters, AnimationType dispatch key, Speed multiplier, open-ended Parameters dictionary
IBattleAnimationPlayerPlays one animation type — Play(anim, onComplete) must invoke the callback so the action machine can advance
AnimationRegistrySingleton index (Instance) keyed by AnimationType; Register() replaces any existing player for the same key (last write wins), Get() looks up

Executors never play animations directly — they request them via IBattleContext.ScheduleAnimation(IBattleAnimation), and the playback layer resolves the matching player from the registry.

Executor routing recap

ActionExecutorHub resolves an action ID in two tiers:

flowchart LR
    A["Execute(action, user, target)"] --> B{"Active provider<br/>set?"}
    B -- "yes" --> C["provider.GetExecutor(id)"]
    C -- "miss" --> D["Global registry<br/>RegisterGlobal(executor)"]
    B -- "no" --> D
    D -- "miss" --> E["Result = false"]
    C -- "hit" --> F["executor.Execute()"]
    D -- "hit" --> F
  • Global tier: ActionExecutorHub.Instance.RegisterGlobal(executor) — the fallback pool, including auto-registered GDScript executors (a .gd file with get_action_id() + execute())
  • Provider tier: the active battle core installs per-core overrides via SetActiveProvider(IActionExecutorProvider)
  • Lookup order: active provider first, global registry as fallback; no match (or a null action) yields ChangedAttributes { Result = false }

Creating a custom battle system mod

  1. Create a new mod with manifest.json:
   {
     "name": "MyBattle",                                   // Human-readable mod name
     "description": "Custom battle system",                // Short description
     "sources": ["src/**/*.cs"],                           // Glob patterns for C# source files
     "depends": ["visual_novel_core"]                                   // Versioned dependency strings
   }
  1. Implement IBattleCore:
       public class MyBattleCore : IBattleCore
   {
       public string Id => "MyBattle";
       public IActionExecutorProvider ActionProvider => new MyActionProvider();

       public void Init(Character[] playerChars, Character[] enemyChars, IBattleContext ctx)
       {
           // Create enemy panels, character widgets, action buttons
       }

       public void Start()
       {
           // Begin turn loop
       }
   }
  2. Implement IActionExecutorProvider to provide your action executors:
       public class MyActionProvider : IActionExecutorProvider
   {
       public IActionExecutor GetExecutor(string actionId)
       {
           return actionId switch
           {
               "mybattle.attack" => new MyAttackExecutor(),
               "mybattle.defend" => new MyDefendExecutor(),
               _ => null
           };
       }
   }
  3. In scenarios, select your core before initiating battle:
       action battle.set_core core=MyBattle
   action battle.init scene=town_entry enemies=wolf_1

Mod Catalog & Network Repository

Source: docs/mods/catalog/index.md - https://cthangover.ru/docs/mods/catalog/index

The mod catalog system lets players browse and install mods from online repositories. A catalog is a JSON file hosted on a web server; the game fetches it, merges entries from multiple URLs, and compares them against locally-installed mods.

  "mods": [                                                // List of mod entries in this catalog
    {
      "id": "live2d",                                      // Canonical mod identifier (matches manifest.json id)

langstringLanguage code (ISO 639-1, e.g. "en", "ru")
namestringLocalized display name
descriptionstringLocalized short description

Resolution order: exact language match → fallback to "en" → first entry in the array → top-level name/description.

Checksums

Two SHA256 hashes are stored per download entry (per version):

archive_sha256 hash of the .zip archive as it sits on the server. The game verifies this after downloading to detect transfer corruption.

install_sha256 hash of the mod's extracted content, computed by:

  1. Enumerating all files in the mod (recursively)
  2. Excluding dot-prefixed files/directories (.godot/, .import/,

    .gitignore) and patterns from catalog_ignore_patterns in mod_config.json

  3. Sorting files by path (case-insensitive)
  4. For each file: SHA256(path_bytes + content_bytes)
  5. Final: SHA256(file_hash_1 + file_hash_2 + ...)

When the game detects that a locally-installed mod's install_sha256 differs from the catalog value, it shows a "Modified locally" warning. Overwriting such a mod from the network would lose the player's changes.

Configuration

Catalog URLs are configured in config/mod_config.json:

{
  "catalog_urls": [                                        // URLs to fetch catalog.json from (merged in order)
    "https://example.com/mods/catalog.json",
    "https://mirror.example.com/mods/catalog.json"
  ],
  "catalog_ignore_patterns": [".*", "bin", "obj"]          // Glob patterns to exclude from install_sha256 computation
}

The code default for catalog_ignore_patterns is [".*"] (ModConfig.CatalogIgnorePatterns), which excludes all dot-prefixed entries. The config/mod_config.json shipped with the game extends this to [".*", "bin", "obj"] to also skip build output directories.

Multiple URLs are merged — when the same mod appears in two catalogs, the entry with the highest version wins for metadata (name, description, category, etc.), while downloads arrays from all sources are merged: same-version entries have their urls lists combined (deduplicated).

The game caches fetched catalogs to user://catalog_cache.json. Open the Network tab in the mods menu (Mods > Network) and press Refresh to clear the cache and re-fetch.

Architecture note: the catalog system provides the data source for an HTTP catalog scanner. For details on how a custom scanner turns catalog JSON into DiscoveredModEntry items that the kernel can load, see Resources — Scanners.

Exporting a mod to the catalog

From the mods menu, select a locally-installed mod and click Export to Catalog. This opens a dialog where you fill in the download URL, category, tags, and changelog, then generates:

  • A .zip archive of the mod (if it was a folder)
  • A .json catalog entry file alongside the archive

Categories are pre-checked from the mod's manifest.json category field (falling back to other when absent); several categories can be toggled at once.

Only Health, Defence, Attack, and Point are typed battle attributes (wrapped in Attribute — see Attribute model). Be honest with yourself about what this gives you:

  • Numbers import as int (or float when fractional), booleans as bool,

    strings as strings; arrays and objects are stored as their raw JSON text.

  • Core code never reads Properties. Keys such as Strength or Fullness

    are inert data unless your own mod code consumes them. They are not typed attributes and take no part in battle math, hunger, or recruiting unless you implement that logic yourself (e.g. in a scenario action or behaviour class).

Battle actions (ActionCharacter)

Every entry in a character's Actions array references an ActionCharacter definition (Core/Characters/ActionCharacter.cs). Actions define what a character can do in battle — attack, defend, stun, heal — together with their targeting category and free-form parameters.

Actions are collected from the same characters/ JSON group as characters themselves (ActionCharacterFactory calls JsonGroup.Collect<ActionCharacterInfo>("characters")), so action definitions live anywhere under your mod's characters/ folder using the usual { "Items": [...] } envelope:

{
  // Wrapping array — action definitions are listed under Items
  "Items": [{
    // Unique action ID — referenced by characters' "Actions" arrays
    "Id": "mymod/fireball",
    // Locale key for the name shown in the battle action menu
    "Name": "characters/action/fireball/name",
    // Locale key for the tooltip text
    "Description": "characters/action/fireball/description",
    // Targeting category: "ToSelf", "ToAlias" (allies), or "ToEnemy"
    "Type": "ToEnemy",
    // Icon sprite path, resolved in the characters texture group
    "Image": "characters/actions/fireball",
    // Flat list of "Key=Value" strings parsed into the Properties bag;
    // everything before the first '=' is the key, the rest is the value
    "Values": [
      "RequiredPoint=2",
      "Attack=3.5",
      "AttackType=Fire"
    ]
  }]
}
FieldDescription
IdUnique action ID, used as the factory lookup key
NameLocale key for the display name in the battle action menu
DescriptionLocale key for the tooltip
TypeTargeting category — ToSelf (caster), ToAlias (allies), ToEnemy (opponents)
ImageIcon sprite resolved via TextureUtils.LoadFromModGroup("characters", ...)
ValuesList of "Key=Value" strings populating the Properties bag

There are no reserved parameter keys at the definition level — core executors read whatever keys they care about (the stock physics actions use RequiredPoint, Attack, AttackType, Defence, Turn), and custom C# executors (IActionExecutor) can read their own via the GetStr / GetInt / GetFloat / GetBool helpers on ActionCharacter.

The visual_novel_core mod keeps its actions in characters/actions/*.json registered through a characters/actions.json index with ${} includes:

{ "Items": [
    ${actions/physics_attack},
    ${actions/physics_defence},
    ${actions/physics_stun}
]}

ActionCharacterFactory.Get(id) returns a copy of the cached definition on every call — action cards carry mutable battle state (cooldowns, modifiers), so character instances never share one instance.

Attribute model

The stat block (CharacterAttributes, Core/Characters/CharacterAttributes.cs) has exactly four attributes, each wrapped in an Attribute object:

AttributeMeaning
HealthHit points (Value = current, BaseValue = max)
DefenceReduces incoming damage
AttackBase damage dealt
PointAction points consumed by abilities

Attribute (Core/Characters/Attribute.cs) mechanics worth knowing when writing battle code:

  • Value — current value; setting it fires OnChange.
  • BaseValue — unmodified maximum.
  • Percent — Value / BaseValue ratio for health bars (0 when BaseValue is 0).
  • Init(int) — sets Value and BaseValue to the same starting value.
  • Copy() — clones Value/BaseValue; OnChange subscribers are not copied.
  • OnChange — a ChangeAttribute delegate (void(float value, float baseValue)).

    It fires on every Value setter call, even when the value didn't change — treat it as a notification mechanism, not a diff detector (a fizzle-heal at full health still triggers UI feedback).

Battle actions report their outcome as a ChangedAttributes struct (Source / Target — CharacterSet snapshots of both sides after the exchange, plus a bool Result success flag). This is what IActionExecutor.Execute(action, user, target) returns; the executor hub matches executors to actions by ActionId.

Factory behavior

  • Minimum coercion — CharacterFactory.CreateCharacter coerces Health and

    Point to a minimum of 1 (Health > 0 ? Health : 1, same for Point); Defence and Attack are taken as-is, including 0.

  • Copies on read — CharacterFactory.Get(id) returns a deep copy per call

    (Character.Copy()): Attributes are cloned and StatusEffectQueue is re-owned by the new instance, so battle mutations never leak into templates.

  • Unknown action IDs are dropped silently when resolving the Actions list.

GDScript API

Auto-registration (convention-based)

GDScript objects loaded by ModGDScriptLoader are automatically scanned for methods starting with on_mod_event_. Each such method is subscribed to the string event bus under the key after the prefix.

# scripts/my_handler.gd
func on_mod_event_scene_entered(data: Dictionary) -> void:
    print("Entered scene: " + data.scene_name)

func on_mod_event_battle_ended(data: Dictionary) -> void:
    print("Battle ended: " + data.result)

func on_mod_event_cooking_meal_ready(data: Dictionary) -> void:
    if data.dish == "wolf_stew":
        boost_morale()

The method receives a Dictionary with snake_case keys (e.g. scene_name, item_id, old_status) matching the typed event properties.

Manual subscription

ModEventBus.subscribe("scene_entered", _on_scene, 0, "my_mod")

func _on_scene(data: Dictionary) -> void:
    print(data.scene_name)

Publishing from scenario actions

GDScript scenario actions can publish events via ctx.PublishEvent():

func get_name() -> String:
    return "cooking.meal_cooked"

func run(ctx) -> void:
    ctx.PublishEvent("cooking_meal_ready", {
        "dish": ctx.GetParam("dish"),
        "quality": ctx.GetParam("quality")
    })

Publishing directly

ModEventBus.publish("cooking_meal_ready", { "dish": "wolf_stew", "quality": 0.8 })

Error isolation

Each handler is executed in a try/catch. An error in one handler does not prevent other handlers from executing. Errors are logged to the EVENT_BUS category.

Cleanup

When a mod is reloaded or unloaded, its subscriptions are removed:

ModEventBus.Instance.ClearForMod("my_mod");

This covers both typed (C#) and string (GDScript) subscriptions for that mod. GDScript mods automatically get ClearForMod called on reload via ModGDScriptLoader.

Typed layer reference

The typed C# layer lives in Core/Events/ModEventBus.cs. All three methods are static and constrained to T : ModEvent:

MethodSignatureNotes
Subscribe<T>Subscribe<T>(Action<T> handler, int priority = 0, string modId = null)priority is only meaningful for [LifecycleEvent] classes (lower = earlier); ignored otherwise
Unsubscribe<T>Unsubscribe<T>(Action<T> handler)Removes a single typed handler
Publish<T>Publish<T>(T evt)Calls all typed handlers first, then auto-bridges to the string layer

Auto-bridge via [EventKey]

On Publish<T>, the bus reads the event class's [EventKey("snake_case_key")] attribute (Core/Events/EventKeyAttribute.cs) and broadcasts a Dictionary on that key so GDScript subscribers receive the same event. Public instance properties declared on the event class itself become snake_case keys (SceneName → scene_name); inherited ModEvent members are not included, and Node references pass through unwrapped. An event class without [EventKey] does not bridge — only typed C# subscribers receive it.

[LifecycleEvent] and delivery order

Marking an event class with [LifecycleEvent] (Core/Events/LifecycleEventAttribute.cs) enables priority-ordered delivery: every Subscribe<T> call re-sorts that event's subscriber list by priority, so lower numbers fire first. Without the attribute, handlers run in subscription order.

Base class ModEvent

All typed events derive from ModEvent (Core/Events/ModEvent.cs), which carries two members available to every handler:

MemberTypeMeaning
SenderModIdstringSending mod (null = engine)
TicklongGame-time tick at publish time (from GameData.Instance.Runtime.Time); 0 if GameData is not yet initialized

Cleanup API

  • ClearForMod(string modId) — removes all subscriptions registered with that modId, across both the typed and string layers. Called on mod unload/reload.
  • ClearAll() — wipes every subscription on both layers.

Any JSON key that does not match a DTO field is captured by ItemInfo.ExtraProperties ([JsonExtensionData]) and imported by ItemFactory into Item.Properties — a string-keyed PropertyData bag (Core/Items/ItemInfo.cs, Core/Items/Item.cs). {
  "Id": "food/ration",
  "...": "...",
  // Captured into Properties — readable from your own code via item.Properties.GetInt("MyMod/Saturation")
  "MyMod/Saturation": 3
}

Item actions (IItemAction)

The ItemAction field references an implementation of IItemAction (Core/Items/IItemAction.cs) — the item's on-use behaviour:

public class MyHealAction : IItemAction
{
    // Registry lookup key — must match the item's "ItemAction" field in JSON
    public string ID => "mymod/heal";

    public bool UseAction(IItem item)
    {
        // Returning FALSE aborts consumption — the item stays in the
        // inventory and the UI can show a failure feedback instead
        return TryHeal(item);
    }
}

Registration options:

  • Auto-discovery — on first use, ItemActionFactory scans every loaded

    assembly for public IItemAction implementations and indexes them by ID. A mod DLL just needs to contain the class — no registration code required.

  • Manual registration — ItemActionFactory.Register(IItemAction) adds a

    single instance; ItemActionFactory.RegisterAssembly(assembly) scans one assembly (used for hot-loaded mod assemblies).

The special ID "null" (or an empty value) is an explicit no-action marker: ItemActionFactory.Get returns null for it, meaning the item has no use effect.

Mod Load Order

Source: docs/mods/load-order/index.md - https://cthangover.ru/docs/mods/load-order/index

The mod load order determines which mod's assets and data take priority when two or more mods define the same resource. The system combines automatic dependency-based ordering with optional manual user overrides.

How ordering works

The game builds the final load order from three inputs, applied in strict priority:

1. depends (manifest.declared) → 2. Manual order (user preference) → 3. Alphabetical (deterministic fallback)

Layer 1: depends — mandatory

Every mod may declare dependencies in manifest.json using versioned dependency strings:

{
  "id": "cooking",                                         // Canonical mod identifier
  "depends": ["visual_novel_core>=1", "interface>=1"]                   // Versioned dependency strings
}

A dependency string has the format: modId[operator][version][?]

Operators
StringMeaningExample
visual_novel_core>=1version ≥ 1.0.0Any core 1.x or higher
visual_novel_core=1.0.0exact matchStrictly 1.0.0
visual_novel_core^1prefix match1.x.x — matches 1.0.0, 1.5.0, but not 2.0.0
visual_novel_core>1greater thanAny version above 1.0.0
visual_novel_core<2less thanAny version below 2.0.0
visual_novel_core<=1less or equalVersion ≤ 1.0.0
visual_novel_coreany versionNo version constraint
visual_novel_core>=1?optionalIf core is installed, must be ≥1; no error if absent

Version comparison is segment-based with zero-padding: 1 equals 1.0 equals 1.0.0. Segments may contain letters (e.g. 1a, alpha-3). Each segment is compared as integer if both sides are parseable, otherwise as string (Ordinal).

Optional dependencies (?)

Appending ? to a dependency makes it optional:

{ "depends": ["optional_mod>=1?"] }                        // ? suffix makes this dependency optional
  • If the optional mod is not installed → no error, the dependency is skipped.
  • If the optional mod is installed → its version must satisfy the constraint.

This is useful for mods that want to react to another mod being present without requiring it.

Strict equality (=) vs prefix match (^)

= requires all segments to match (with zero-padding):

  • visual_novel_core=1.0 does not match 1.0.5 — the third segment "0" ≠ "5".
  • visual_novel_core=1.0.0 matches 1.0.0.

^ matches only the specified segments, ignoring the rest:

  • visual_novel_core^1.0 matches 1.0.0, 1.0.5, but not 1.1.0.
  • visual_novel_core^1 matches 1.0.0, 1.1.0, 1.9.0, but not 2.0.0.

This follows the convention used by npm, Cargo, pip, Factorio, and Minecraft Fabric.

conflicts_with

Mods can declare mutual incompatibility:

{
  "id": "ff_battle",                                       // Canonical mod identifier
  "conflicts_with": ["card_battle"]                        // Declared incompatible mod IDs — informational only
}

!!! warning "Declarative metadata only" conflicts_with is parsed from the manifest and copied into catalog exports, but it is never enforced at runtime. Declaring a conflict disables nothing, blocks nothing, and shows no UI warning — two mods that declare each other as conflicting will still load and run together. Treat this field purely as informational metadata (e.g. for catalogs and mod platforms); do not rely on it to prevent broken combinations.

Layer 2: Manual order — user preference

In the Mods menu (accessed from the main menu), each mod row has ▲▼ buttons. Moving a mod up increases its priority (its files override mods below it); moving a mod down decreases priority.

The manual order is saved per device in user://mod_load_order.json — it does not transfer between devices or affect other players.

Move buttons are disabled when the move would violate a dependency: you cannot move a mod above its own dependency, or below a mod that depends on it.

Layer 3: Alphabetical — deterministic fallback

When two mods have no dependency relationship and no manual order preference, they are sorted alphabetically by their mod ID. This guarantees the same result on every device and operating system.

Conflict resolution strategy

The game uses "last wins" — the mod later in the load order overrides earlier mods:

Asset typeResolution
TexturesSame-name texture from a later mod overrides the earlier one
JSON data (characters, items, recipes, quests, interactives)Same ID entry from a later mod overrides the earlier one
Files (audio, prefabs, etc.)Same-path file from a later mod overrides the earlier one
ShadersSame-name shader from a later mod overrides the earlier one
Locale stringsSame key from a later translation file overrides the earlier one
Scene definitionsMultiple mods can contribute to the same scene — they accumulate
Scenario definitionsAccumulated and sorted by their own priority and after metadata
Property arraysArrays in ExtraProperties (e.g. Skills: ["a"]) are concatenated across patches, not overwritten

When a resource is overridden, a Warning is logged so you can inspect the conflict. The Mods menu also shows a Conflicts section for the selected mod, listing which resources it overrides and which mods override its resources.

Version validation

On load, the game validates all dependency versions:

  • If a required dependency is missing or its version is too low/too high → the mod is disabled with an error.
  • conflicts_with is not validated — see the warning above; declared conflicts never disable anything.
  • Disable reasons are accumulated (not overwritten) and shown in the UI status label.
  • Cascade: if mod A is disabled, all mods depending on A are also disabled.

UI overview

The Mods menu shows:

  • Order number — position in the load order (leftmost column)
  • Mod name, version, thumbnail
  • Enable/disable toggle — disable cascades to dependents
  • ▲▼ buttons — move mod up/down in load order
  • State — button is greyed out when movement is blocked by dependency constraints
  • Status — shows all reasons a mod is disabled (version mismatch, missing dependency)
  • Conflicts — list of resources overridden by or overridden in this mod

Storage

Manual load order is saved to user://mod_load_order.json as a JSON array of mod IDs:

["visual_novel_core", "cooking", "hunting", "ui_overhaul"]              // Mod IDs in manual load order (first = highest priority)

New mods (not yet in the saved order) are placed alphabetically within their dependency level — no manual position is assigned until the user explicitly reorders them.

Removed mods are cleaned up automatically on the next game launch.

For mod creators

Declare dependencies with version constraints for safety:

{
  "id": "my_mod",                                          // Canonical mod identifier
  "depends": ["visual_novel_core>=1", "interface>=1"],                  // Versioned dependency strings
  "version": "1.0.0"                                       // Semver version of this mod
}
  • Use >=1 (not >=1.0.0) — trailing zeros are unnecessary due to zero-padding comparison.
  • Declare conflicts_with for documentation/catalog purposes if your mod is incompatible with another — remember it is informational only and not enforced.
  • Use ? for optional soft dependencies.

Scene Event Metadata

Source: docs/mods/metadata/index.md - https://cthangover.ru/docs/mods/metadata/index

The [SceneEvent] attribute allows mod C# code to hook into scene lifecycle events declaratively, without needing manifest subscriptions.

[SceneEvent] attribute

Place the attribute on a class in a mod assembly to register it for automatic execution. Only classes deriving from ExecutableEvent are registered (Core/Scenes/SceneEventRegistry.cs skips any other type):

using Cthangover.Core.Scenes;
using Cthangover.Core.UI.Executable;

[SceneEvent("home_kitchen", Priority = 5)]
public class KitchenInitEvent : ExecutableEvent
{
    // Runs when home_kitchen scene loads, ordered within the
    // scene's event chain by its Priority / After metadata
}

[SceneEvent("town_entry", After = "other_event")]
public class TownEnterEvent : ExecutableEvent
{
    // Runs after the event whose ID is "other_event"
}

There is no method-based registration and no SceneContext parameter — the attribute cannot be applied to methods (AttributeUsage(AttributeTargets.Class, AllowMultiple = false)).

Attribute parameters

ParameterTypeDescription
SceneNamestring(positional, required) Target scene name
PriorityintExecution order (lower = earlier). Default 0
AfterstringName of another handler this should run after
ConditionstringCondition expression — handler only runs if expression is true

Registration

SceneEventRegistry uses reflection at assembly load time to discover all classes decorated with [SceneEvent]. Only types deriving from ExecutableEvent register; decorated classes without that base type are silently skipped. No manual registration is needed — the attribute itself serves as registration.

Execution order

[SceneEvent] classes are not a separate phase: SceneManager.ComposeEvents composes them into the same event chain as .scenario definitions. That composition runs as a SceneEnteredEvent bus subscriber at priority 15, while manifest subscriptions execute at priority 20 (i.e., after scenario chains). So the order on scene enter is:

  1. Scenario chain events + [SceneEvent] class events, interleaved and sorted by their own priority / After metadata (bus priority 15)
  2. Manifest subscriptions fire afterwards (bus priority 20, ordered among themselves by their priority field)

On scene exit:

  1. on_exit manifest subscriptions fire (by priority)

depends — version syntax

Each depends entry is a string [modId][op][version][?], parsed by ModDependency.Parse (Core/Mods/ModDependency.cs):

{
    "depends": [
        "visual_novel_core",           // bare id — any version
        "visual_novel_core>=1",        // core 1 or newer
        "my_lib^1.2.0",   // version starting with segments 1.2.0
        "extra_icons<2",
        "soft_dep?"       // trailing ? — optional dependency
    ]
}
OperatorMeaning
(none)Any version — bare "modId"
>= / <= / > / <Per-segment comparison against the dependency's actual version
=Exact match (segment-wise)
^Prefix match — required segments must equal the leading segments of the actual version
  • A trailing ? marks an optional dependency: if the mod is missing, that is not an error; if present, its version is still checked.
  • Comparison goes through VersionHelper.CompareSegments (Core/Utils/VersionHelper.cs): both version strings are split on ., both segment arrays are padded with "0" to equal length, and each segment compares numerically if both parse as int, otherwise via ordinal string comparison. Segments may contain letters (1a, alpha-3, 1b.2.0).
  • Entries are read from JSON by ModDependencyListConverter: malformed strings are logged as errors, kept with IsValid = false, and reported later during ValidateDependencies.
  • Valid dependency IDs also drive load order: ModRegistry.GetOrderedModIds topologically sorts so dependencies always precede their dependents.

depends_native — native libraries

depends_native lists glob patterns (e.g. "bin/*.dll", "native/*.so", "lib/*.dylib") for native shared libraries shipped inside the mod. ModNativeLoader.LoadNativeDlls (Core/Mods/ModNativeLoader.cs), called from ModRegistry.Initialize() before managed mod code runs:

  1. Collects platform-appropriate files (.dll on Windows, .so on Linux, .dylib on macOS)
  2. Copies them to the cache directory (user://mod_cache/native/) so zip-based mods can serve native code
  3. Registers a DllImportResolver so P/Invoke ([DllImport]) declarations resolve against the mod-provided native code

If multiple mods provide the same library name, the first one wins; duplicates are logged as warnings. On reload, ModRegistry.Reload() calls ModNativeLoader.FreeAll() to release all native handles so the files can be overwritten on the next load cycle.

Precompiled DLLs (dll/ directory)

A mod may ship precompiled .NET assemblies in a dll/ directory. During ModRegistry.Initialize(), ModAssemblyLoader.LoadPrecompiledDlls (Core/Mods/ModAssemblyLoader.cs) scans that directory recursively, copies each .dll to the assembly cache ({modId}_dll_{fileName}), loads it, and runs the standard RegisterAssembly fan-out (the same registries listed on the C# Source Code page).

This runs before Roslyn compilation of sources, so source-based mods can reference types from precompiled API assemblies. Each loaded precompiled assembly also gets a DllImportResolver installed (ModNativeLoader.InstallResolverOnAssembly) for its own P/Invoke calls.

Array Operations & Identity Keys

Source: docs/mods/patches/arrays-and-identity.md - https://cthangover.ru/docs/mods/patches/arrays-and-identity

Array Operations

When a patch modifies a JSON array property (e.g. Skills, Perks, Tags), the suffix on the key determines how the arrays are merged:

Key suffixBehaviour
(no suffix)Overwrite — replaces the entire array. Same semantics as scalar properties.
$addAdd — appends incoming elements to the existing array. If the property doesn't exist yet, creates it.
$removeRemove — removes incoming elements from the existing array. If the property doesn't exist, no-op.
$setOverwrite — explicit form, same as bare key.

Examples

Base character definition (in characters/player/marao.json):

// Base entity definition
{ "Id": "Marao", "Skills": ["slash", "block"] }  // Id is the entity identifier; Skills is the array to patch

Add elements — a cooking mod extends skills:

// patches/characters.json
// $add appends elements to the existing array (creates if missing)
{ "Items": [{ "Id": "Marao", "Skills$add": ["cook"] }] }

Result: ["slash", "block", "cook"]

Remove elements — a balance patch removes a skill:

// $remove deletes matching elements from the array (no-op if missing)
{ "Items": [{ "Id": "Marao", "Skills$remove": ["block"] }] }

Result: ["slash", "cook"]

Replace entirely — a weapon overhaul resets skills:

// $set replaces the entire array (explicit form, same as bare key)
{ "Items": [{ "Id": "Marao", "Skills$set": ["sword", "shield_bash"] }] }

Result: ["sword", "shield_bash"]

Overwrite (bare key) — equivalent to $set:

// Bare key overwrites the entire array (same as $set); previous values discarded
{ "Items": [{ "Id": "Marao", "Skills": ["slash", "block"] }] }

Result: ["slash", "block"] (previous values are discarded)

Multi-layer example

All three operations can be combined across mod layers. Processing order follows the standard property pipeline (entity → wildcard * → specific Id):

// Entity base: ["slash", "block"]

// Wildcard patch: $add appends "dodge" to ALL entities first
{ "Items": [{ "Id": "*", "Skills$add": ["dodge"] }] }
// → ["slash", "block", "dodge"]

// Specific patch: $remove deletes "slash" from Marao only
{ "Items": [{ "Id": "Marao", "Skills$remove": ["slash"] }] }
// → ["block", "dodge"]

No deduplication is performed — if the same element is added twice, it appears twice.

Universality

This system applies to any array property on any entity type — characters, items, and any mod-defined extras. There is no special-casing for specific property names.

// Works for any array property — no special-casing needed
{ "Items": [{ "Id": "sword/iron", "CraftingMaterials$add": ["steel_ingot"] }] }   // Specific item patch
{ "Items": [{ "Id": "*", "Tags$add": ["undead"] }] }                                // Wildcard: tags all entities

Scalar properties (int, float, bool, string) still use last-wins semantics — the suffix convention only affects JSON array values.

Object Arrays with Identity Keys

⚠ IMPORTANT CONVENTION: the identity field MUST be named Id (or end in Id, like ItemId, QuestId, ActionId).

For mod-defined (extra-property) arrays this field is auto-detected — no registration, no config, no C# code needed. For typed C# array properties there is a second path: if the element type implements IMergeable, its MergeKeyProperty value is used first, taking priority over the naming convention (see below).

For arrays of objects (e.g. Loot, Rewards, Drops), the system matches elements by an identity field instead of raw JSON text. This enables per-field merge: a patch can update a single property of an existing object without repeating all its fields.

How identity detection works

Resolution order per property:

  1. Interface first — if the entity type is known and the array property's

    element type implements IMergeable (Core/Mods/Patches/IMergeable.cs, a single MergeKeyProperty string property), the key comes from MergeKeyProperty. The map is built by JsonPatchMerger.BuildMergeKeys<T>(). Example: LootEntry (Core/Characters/LootEntry.cs) implements IMergeable with ItemId as its key, so the typed Loot property always merges by ItemId.

  2. Convention fallback — when no interface-provided key exists, the key is

    auto-detected from the array JSON itself (table below).

Array element typeDetectionIdentity field
{"Id": "gold", ...}First field named Id → detectedId
{"ItemId": "sword", ...}No Id, but field ending in Id → detectedItemId
{"QuestId": "q1", ...}Same logicQuestId
{"Name": "test"}Nothing matches → no identityRaw text compare
"string" or 42Not an object → no identityRaw text compare

The system prioritises exact "Id" over suffix matches. If your object has both Id and ItemId, Id wins.

Per-field merge example

// Base entity: object array with ItemId as identity key
{ "Loot": [
    {"ItemId": "food/wolf_meat", "MinCount": 1, "MaxCount": 1, "Probability": 100},    // Matched by ItemId
    {"ItemId": "resource/branches", "MinCount": 1, "MaxCount": 1, "Probability": 100}  // Matched by ItemId
]}

// Balance patch: uses $add/$remove on the object array
{ "Items": [{ "Id": "wolf_1",
    "Loot$add": [{"ItemId": "food/ration", "Probability": 50}],        // Adds new entry
    "Loot$remove": [{"ItemId": "resource/branches"}]                    // Removes by identity match
}]}

// Result:
// → food/wolf_meat: unchanged
// → resource/branches: removed (matched by ItemId)
// → food/ration: added as new entry

Per-field property overwrite

When $add finds an existing element with the same identity value, the patch overwrites only the specified properties, preserving unmentioned fields from the base:

// Base: {"ItemId": "food/bread", "MinCount": 1, "MaxCount": 2, "Probability": 50}
// Patch: {"Loot$add": [{"ItemId": "food/bread", "Probability": 80}]}   // Matches by ItemId, merges only Probability
// Result: {"ItemId": "food/bread", "MinCount": 1, "MaxCount": 2, "Probability": 80}
//         (Probability overridden, MinCount/MaxCount preserved from base — per-field merge)

Removing with identity key

The $remove operation only needs the identity field — other fields in the remove object are ignored:

// $remove only needs the identity field (ItemId); other fields are ignored
{ "Items": [{ "Id": "wolf_1", "Loot$remove": [{"ItemId": "food/wolf_meat"}] }] }

Mod-defined arrays — no config needed

Any mod can introduce a new array of objects in a character or item JSON, and patches immediately work with per-field merge — as long as objects have an Id or *Id field:

// Mod A defines a quest with rewards (identity key: Id)
{
  "Id": "daily_hunt",
  "Name": "Daily Hunt",
  "Rewards": [
    {"Id": "gold", "Count": 100},     // Identity field "Id" detected automatically
    {"Id": "exp", "Count": 50}
  ]
}

// Mod B patches the rewards without knowing Mod A's internals:
{ "Items": [{ "Id": "daily_hunt",
    "Rewards$add": [{"Id": "gold", "Count": 200}],   // Matched by Id → overwrites Count, preserves Id
    "Rewards$remove": [{"Id": "exp"}]                 // Matched by Id → removes entire exp entry
}]}

// Result Rewards: [{"Id": "gold", "Count": 200}]

No C# code, no interface, no registration is needed for mod-defined extra-property arrays — the Id / *Id convention is all that's required. The IMergeable interface is an optional, higher-priority path for typed C# array properties (see the resolution order above); it does not need to be implemented for convention-based detection to work.

Patches

Source: docs/mods/patches/index.md - https://cthangover.ru/docs/mods/patches/index

Patches let one mod add or override properties of entities defined in another mod — without rewriting their JSON files entirely.

  • "Id": "EntityName" — apply only to the entity with this ID.
  • "Id": "*" — wildcard: applies to all entities of this type, serving as a fallback value. An entity's own JSON-defined properties always take precedence over wildcard values.

Works for characters (characters) and items (items).

Overview

Each mod can contain an optional patches/ directory. Patch sources are collected by PatchResolver (Core/Mods/Resolvers/Impls/PatchResolver.cs), which scans both layouts per entity type:

mods/
└── my_mod/
    └── patches/
        ├── characters.json         ← flat file: patches for characters
        ├── items.json              ← flat file: patches for items
        └── characters/             ← directory form: any *.json inside is scanned too
            ├── player.json
            └── enemies.json
  • Flat files: patches/{entityType}.json (e.g. patches/characters.json)
  • Directory form: every .json inside patches/{entityType}/

Both forms use the same format below; results from all mods are grouped by target entity id. From C#, patches are collected via the static facade Patches.Collect(entityType), which proxies through ModManager.Instance.GetResolver<PatchResolver>() (results are cached per type until ClearCache()).

Format

Standard {"Items": [...]} wrapper. Each entry contains an Id and arbitrary properties to add:

{
  "Items": [
    {
      "Id": "Marao",                    // Id matching: applies only to entity with this exact Id
      "TestPatched": 42,                // Arbitrary property added via patch
      "TestDefault": 100                // Will be layered over wildcard values
    },
    {
      "Id": "*",                        // Wildcard: applies to ALL entities as a fallback
      "TestDefault": -20,               // Overridden by entity's own properties or specific patches
      "TestGlobalPatch": 1              // Global property applied to all entities
    }
  ]
}

Property Resolution Order

When creating an entity, its properties are assembled in layers. Each subsequent layer overwrites keys from the previous ones:

LayerSourcePriority
1Entity's own properties (from its JSON)Base
2Wildcard patches "*" (in mod load order)Higher
3Targeted patches by Id (in mod load order)Highest

Patches from Different Mods

Patches accumulate: each mod adds its entries to the list for the target ID. When applied, they are iterated in load order, and a later mod overwrites keys of an earlier one.

Mod A:

// Wildcard patch adds Test and Strength to all characters
{ "Items": [{ "Id": "*", "Test": -20, "Strength": 10 }] }

Mod B (loaded after A):

// Mod B (loaded after A): overwrites Test but preserves Strength
{ "Items": [{ "Id": "*", "Test": 0 }] }

Result for all characters: { "Test": 0, "Strength": 10 } — Test overridden, Strength preserved.

Full Example

  "Strength": 15

// mods/mod_b/patches/characters.json
{

    { "Id": "*", "Test": -20, "CritChance": 5, "GlobalBuff": 10 }      // Wildcard: fallback for all other characters
  ]

Two kinds of status — don't conflate them

A quest carries two independent state values (Core/Quests/):

WhereTypeWhat it meansHow it changes
QuestBase.StatusQuestStatus enum (byte)Quest lifecycle — not started / active / finishedquest.set_status → QuestService.SetStatus
QuestData.Status (i.e. quest.Data.Status)raw intNumeric stage counter used for journal descriptions and fine-grained progressquest.set_data_status level=N → QuestService.SetDataStatus

They are stored and mutated separately. Setting one does not touch the other.

QuestStatus enum

QuestStatus (Core/Quests/QuestStatus.cs) is a byte-sized enum with exactly three values:

NameValueMeaning
NotStarted0Never accepted or activated; hidden from the journal by default
Progress1Accepted, possibly with sub-objectives tracked via tags
End2Terminal completed state

action quest.set_status expects the status names above as the status parameter; parsing via Enums<QuestStatus>.Parse is case-insensitive (notstarted, Progress, END all work). Invalid names are logged and the call is ignored.

Quest tags

Quests use a tag system to track progress. Tags are set via scenario action commands:

action battle.init scene=town_entry enemies=wolf_2,werewolf_girl_1 quest_id=MeetingMurakamiQuest new_tag=boss_battle

This sets the tag boss_battle on MeetingMurakamiQuest when the battle is initiated.

On the C# side, tags live in a HashSet<string> on QuestBase.Data (Core/Quests/QuestBase.cs):

MethodDescription
AddTag(tag)Adds a milestone tag
RemoveTag(tag)Revokes a tag (no-op if absent)
ContainsTag(tag)Membership check
NotContainsTag(tag)Negated membership check

Scenario condition: expressions map onto these directly: hasTag(...) calls IQuest.ContainsTag, notHasTag(...) calls IQuest.NotContainsTag (resolved by QuestMethodCondition, Core/Scenes/QuestMethodCondition.cs).

Conditional scenarios

Scenarios use quest tags in their condition: metadata to decide whether they should run:

scene: town_entry
priority: 20
condition: MeetingMurakamiQuest.hasTag("wolf_battle") && MeetingMurakamiQuest.notHasTag("boss_battle")
---
background "town/meetingmurakami/00002-1920617752"
text "[Wolf tracks lead to the door]" key=meeting/after_wolf/tracks

This scenario only executes if:

  1. The player killed the wolf (hasTag("wolf_battle"))
  2. The player has NOT yet fought the boss (notHasTag("boss_battle"))

Status progression in practice

The journal reads the current numeric stage (quest.Data.Status) and displays the matching locale key from StatusToDescription. Stage advancement happens via C# or scenario actions:

action quest.set_data_status quest_id=PrologQuest level=1

Lifecycle changes use the named statuses instead:

action quest.set_status quest_id=PrologQuest status=Progress

To surface a "new journal entry" banner after changing quest state, call:

action quest.send_notification quest_id=PrologQuest

Under the hood this routes to IQuestExtensions.SendNotification(this IQuest) (Core/Quests/IQuestExtensions.cs), which posts a localized ui/journal/new - <quest name> message to the notification banner queue. It does not modify quest state.

Events emitted

Both events are published from QuestServiceImpl (Core/Actions/QuestServiceImpl.cs) and reach GDScript mods through the ModEventBus string layer (payload keys are snake_case versions of the C# properties):

Note: tag events fire even when the target quest ID doesn't exist (the state mutation is skipped, the event still publishes).

Persistence pipeline

QuestFactory (Core/Quests/QuestFactory.cs) owns quest instances end-to-end:

  • QuestFactory.Instance.Get(id) — returns the shared runtime QuestBase.

    Throws KeyNotFoundException when the id was never loaded from mod data (typically a typo in a scenario reference).

  • QuestFactory.Instance.GetAll() — snapshot list of every known quest; used

    by the save system to serialize full quest state.

  • QuestFactory.Instance.SetAll(List<QuestBase>) — save/restore: looks up each

    entry from the save file by ID and overwrites its Data (tags + stage) and lifecycle Status. Empty/null lists are ignored.

Scenario-facing QuestService methods wrap the factory with an internal safe-get, so a missing quest in an action command logs an error instead of crashing the scenario.

IRecruitCondition

A gating predicate consulted before any recruitment roll happens (Core/Relationship/IRecruitCondition.cs). Conditions receive the defeated Character and the full RuntimeData, so they can inspect stats, quest state, inventory, or relationship flags:

public class MyRecruitCondition : IRecruitCondition
{
    // Unique identifier for debugging and override lookups
    public string Id => "my_mod/level_cap";

    public bool CanRecruit(Character enemy, RuntimeData runtime)
    {
        return enemy.Level <= 5;
    }
}

Rules:

  • Conditions are auto-discovered from mod assemblies via

    RecruitBehaviourRegistry.RegisterAssembly — just ship a public class.

  • The gate is conjunctive: all discovered conditions must return true.

    A single false blocks recruitment for that enemy — mods compose gates without coordinating with each other.

  • If no conditions are registered at all, the gate passes vacuously.

RecruitTickController

Periodic tick handler that processes recruit-related updates (e.g. hunger depletion, status regeneration). Runs on a timer.

Recruitment flow

  1. Character is defeated in battle (WingroundBehaviour.ProcessRecruitment)
  2. Enemies with RecruitmentChance > 0 are passed through the condition gate:

    RecruitBehaviourRegistry.CanRecruit must return true (all IRecruitConditions pass)

  3. The engine rolls 1–100 against the enemy's RecruitmentChance
  4. On success the enemy is registered as a recruit via RecruitingData.Add
  5. On acceptance in the UI: character.add_to_party action fires → CharacterData.AddCharacterToParty() → creates CharacterInfoData entry
  6. Character joins the battle set and becomes controllable

Scenario integration

Use character.add_to_party to recruit directly from a scenario:

action character.add_to_party type=Murakami

Show a notification without roster changes:

action character.send_notification type=Murakami

Custom recruit behaviour

Implement IRecruitBehaviour to add custom logic on recruit lifecycle events. Implementations are auto-discovered from mod assemblies via RecruitBehaviourRegistry.RegisterAssembly. Because dispatch is cross-recruit — each behaviour receives every active recruit on each event — a behaviour can also introspect other recruits:

public class MyRecruitBehaviour : IRecruitBehaviour
{
    // Unique identifier for RecruitBehaviourRegistry.Get lookup
    public string Id => "my_mod/loyalty";

    public void ConfigureRecruit(Recruit recruit, RuntimeData runtime)
    {
        // Called when a recruit is added — set initial properties;
        // RecruitingData.Add returns the instance, but this hook fires too
        recruit.Properties.SetInt("loyalty", 50);
    }

    public void OnTick(Recruit recruit, RuntimeData runtime, long currentTick)
    {
        // Called every game tick for each active recruit;
        // currentTick is RuntimeData.Time.Tick — use it for periodic logic
    }

    public void OnRemove(Recruit recruit, RuntimeData runtime)
    {
        // Called when a recruit is removed — clean up state
    }
}

Relationship to skills

Recruited characters can acquire skills. SkillData is not a singleton — it is a plain instance owned by RuntimeData, accessible as GameData.Instance.Runtime.SkillData. It holds a single global set of player-owned skill IDs (lowercase strings such as "slave_master") and is persisted with the save. Skills are not tied to individual recruits — they are a global unlock pool.

Mod Save API

Source: docs/mods/save/api.md - https://cthangover.ru/docs/mods/save/api

Implementing IModSaveable in a mod

Your mod must provide a class implementing IModSaveable. It is auto-discovered via reflection when your mod assembly loads.

API

public interface IModSaveable
{
    // Called on save. Slot metadata (ModId, ModName, ModVersion) is
    // already filled by the core. Set MinCoreVersion, IsRequired,
    // CustomData, and write Data[...].
    void OnSave(ModSlot slot);

    // Preferred: explicit contract. Return false + error message on
    // failure. Default impl calls OnLoadVoid for backward compat.
    bool OnLoad(ModSlot slot, out string errorMessage);

    // Legacy: throw-based error handling. Override instead of OnLoad
    // if you prefer exceptions for error reporting.
    void OnLoadVoid(ModSlot slot);
}

Minimal example

using Cthangover.Core.Mods;
using Cthangover.Core.Settings;

public class MyModSaveHandler : IModSaveable
{
    public void OnSave(ModSlot slot)
    {
        // ModId, ModName, ModVersion already set by core.
        // Set only what the core needs for validation:
        slot.Metadata.IsRequired = true;

        var blob = new DataBlob();
        blob.SetInt("Health", player.Health);
        blob.SetInt("Mana",   player.Mana);
        blob.SetString("Name", player.Name);

        slot.Data["Stats"] = blob;
    }

    public bool OnLoad(ModSlot slot, out string errorMessage)
    {
        if (slot.Data.TryGetValue("Stats", out var blob))
        {
            player.Health = blob.GetInt("Health", 100);
            player.Mana   = blob.GetInt("Mana", 50);
            player.Name   = blob.GetString("Name", "Hero");
            errorMessage = null;
            return true;
        }

        errorMessage = null;
        return true; // No data → nothing to restore, not an error
    }
}

Versioned migration

When your data schema changes, use DataBlob.Version to handle migration:

public void OnSave(ModSlot slot)
{
    var data = new PlayerStateV2 { Health = 80, Mana = 40, Stamina = 100 };
    slot.Data["FullState"] = new DataBlob(version: 2, data);
}

public bool OnLoad(ModSlot slot, out string errorMessage)
{
    if (!slot.Data.TryGetValue("FullState", out var blob))
    {
        errorMessage = null;
        return true; // no data — nothing to restore
    }

    if (blob.Version == 2)
    {
        var state = blob.ReadJson<PlayerStateV2>();
        Apply(state);
        errorMessage = null;
        return true;
    }

    if (blob.Version == 1)
    {
        var old = blob.ReadJson<PlayerStateV1>();
        Apply(new PlayerStateV2
        {
            Health  = old.Health,
            Mana    = old.Mana,
            Stamina = 100, // default for new field
        });
        errorMessage = null;
        return true;
    }

    errorMessage = $"Unsupported data version: {blob.Version}";
    return false;
}

Binary data

DataBlob can hold raw bytes: construct it from a byte[], or use the binary API (GetBytes/SetBytes) to read and write raw data.

public void OnSave(ModSlot slot)
{
    slot.Data["Skin"] = new DataBlob(textureBytes);
}

public bool OnLoad(ModSlot slot, out string errorMessage)
{
    if (slot.Data.TryGetValue("Skin", out var blob))
    {
        byte[] bytes = blob.GetBytes();

Marking a mod as optional

If a save can be loaded without your mod, set IsRequired = false:

slot.Metadata.IsRequired = false;

The core will log a warning and skip the mod's data if the mod is not installed.

Compatibility guard (MinCoreVersion)

If your save data depends on a specific core API, set the minimum version:

slot.Metadata.MinCoreVersion = "0.2.0";

On load, if the current core version is below 0.2.0, the load is aborted with an error message.

Source: docs/mods/save/index.md - https://cthangover.ru/docs/mods/save/index

Core concepts

Uniform slots

Every piece of persisted state lives in a ModSlot under SavePackage.ModData. There is no distinction between "core" and "mod" data at the storage level — the core just happens to own the reserved key "__core__".

Dispatcher (core)

The core is a lightweight dispatcher. It:

  • Builds its own "__core__" slot with named DataBlob blocks per subsystem.
  • Collects slots from mods and merges them into the save package.
  • Validates mod metadata on load (required mods present, version compatibility).
  • Never inspects mod data contents — it works only with byte arrays and version numbers.

Load flow (three phases)

  1. Phase 1 — Validation (via ModMetadata of every slot):
    • For each ModSlot in ModData:
      • If IsRequired == true and the mod is not installed → abort.
      • If CoreVersion < MinCoreVersion → abort.
      • Mod version comparison (if both save and installed mod have versions):
        • save.Version > installed.Version → abort (downgrade not supported).
        • save.Version < installed.Version → warning (mod must handle migration in OnLoad).
  2. Phase 2 — Core state restore: read blobs from ModData["__core__"] and push values into RuntimeData.
  3. Phase 3 — Mod dispatch (ModSaveableRegistry.DispatchLoad):
    • For each installed mod whose ID is in ModData (excluding "__core__"), call OnLoad(slot, out error).
    • Two overloads supported: bool OnLoad(ModSlot, out string) and legacy void OnLoadVoid(ModSlot) (throw on error).

Reserved slot key

The key "__core__" is reserved for the core game state. If a mod attempts to write a slot with this key, the save service logs a warning and skips it.

Versioning & Compatibility

Source: docs/mods/save/versioning.md - https://cthangover.ru/docs/mods/save/versioning

Backward compatibility

Old saves (without ModData, SaveId, Timestamp, CoreVersion fields) will fail to load because the "__core__" slot is required. The old SaveData format must be migrated manually or via a one-time converter tool.

Version comparison

During phase-1 validation the core compares ModMetadata.ModVersion from the save with IModInfo.Version from the installed mod. Both values originate from the "version" field in manifest.json.

Comparison strategy

The core uses per-segment comparison via VersionHelper.Compare (Core/Utils/VersionHelper.cs). There is no System.Version parsing anywhere — the algorithm is:

  1. Both strings are trimmed and split on .. The shorter segment array is padded with "0" to equal length ("1.0" equals "1.0.0").
  2. Segments are compared pairwise, left to right. For each position: if both segments parse as int, they are compared numerically (handles "9" < "10"); otherwise that segment pair is compared with an ordinal string comparison (String.CompareOrdinal).
  3. The first non-zero comparison decides the result.

Consequences: a segment like "1b" does not parse as int, so it compares ordinally, not numerically. Mixed versions are fine — each segment independently picks numeric or ordinal comparison.

Supported version formats

FormatExampleComparison
Numeric segments1.0.0, 2.5.3.1, 1.0Numeric per segment; shorter string padded with "0"
Letter in a segment1b.2.0That segment compares ordinally ("1b" vs "10" is ordinal, not numeric)
Prefixed tagsv1, v2.0Ordinal per segment ("v2" > "v10" ordinally)
Codename-styleEnigma1.5, Enigma2.0Ordinal per segment
Alpha/beta tagsalpha-1, beta-3Ordinal per segment

Validation rules

ConditionResult
No version in save or installed modSkip check
save.Version > installed.VersionAbort — save was made by a newer mod; downgrade not supported
save.Version < installed.VersionWarning — save is from an older mod version; the mod must handle migration in OnLoad
save.Version == installed.VersionOK

Adding version to manifest.json

Every mod's manifest.json must include a semver version string:

{
  "name": "My Mod",                                        // Human-readable mod name
  "version": "1.0.0",                                      // Semver version — used for save validation and migration detection
  "author": "...",                                         // Author credit
  "description": "...",                                    // Short description
  "sources": ["src/**/*.cs"]                              // Glob patterns for C# source files
}

This value flows through ModManifest.Version → IModInfo.Version → ModMetadata.ModVersion and is used for the save-system version checks above.

Important rules for mod authors

  • Add "version" to manifest.json — the core uses it for save validation and migration detection.
  • One IModSaveable per mod — create a single implementation in your assembly.
  • Never set ModId, ModName, or ModVersion — the core pre-fills them. Set MinCoreVersion, IsRequired, CustomData, and Data.
  • Prefer bool OnLoad(ModSlot, out string) — explicit contract, no exceptions. Override OnLoadVoid only for legacy/compatibility.
  • Mods must not depend on each other's save data — the dispatch order is undefined.
  • Version your DataBlob blocks — use separate blobs per logical entity, version each independently.
  • Handle missing keys — use TryGetValue and provide defaults.

Scene lifecycle

When the player enters a scene, the engine:

  1. Loads defaultBackground as the background image
  2. Starts defaultAmbient playlist (if set)
  3. Loads and executes defaultScenario
  4. Fires on_enter subscriptions from all mods (by priority order)
  5. When leaving, fires on_exit subscriptions

Mod subscriptions to scenes

Mods hook into scene lifecycle via their manifest.json:

{
  "subscriptions": [
    {
      "scene": "home_kitchen",      // Target scene ID to hook into
      "template": "default",        // Wrapper template name (from wrappers/ directory)
      "code": "cooking_panel_init", // C# code fragment name (from subscriptions/{name}.cs)
      "trigger": "on_enter",        // Lifecycle event: on_enter or on_exit
      "priority": 10                // Execution order (lower = earlier); multiple mods sorted by priority
    },
    {
      "scene": "home_kitchen",
      "template": "default",
      "code": "dinner_tools_hide",
      "trigger": "on_exit",
      "priority": 10
    }
  ]
}

Multiple mods can subscribe to the same scene — they run in priority order. This is how the Cooking mod adds a "Cook" option to the kitchen scene without modifying visual_novel_core.

Scenario priority system

Multiple .scenario files can target the same scene:. The one with the lowest priority number runs first. If that scenario's condition: is unmet, the next-highest priority scenario is tried.

flowchart LR
    A["home_kitchen_cooking.scenario<br/>priority: 5"] -->|runs first| S{{"Scene:<br/>home_kitchen"}}
    B["home_kitchen_default.scenario<br/>priority: 10"] -->|fallback| S

This allows mods to extend scenes non-destructively by writing additional scenario files with lower priority numbers.

Adding a new scene

  1. Create scenes/{name}.json with background, playlist, and default scenario
  2. Create the background image(s) in backgrounds/{name}/
  3. Write the default scenario in scenarios/{path}.scenario
  4. Add switch_scene {name} commands to an existing scene to create a navigation path
  5. Register on_enter/on_exit subscriptions in your manifest if needed

How the engine selects scenarios

  1. Player enters scene: home_kitchen
  2. Engine collects all .scenario files targeting home_kitchen across all mods
  3. Sorts by priority (ascending) and resolves after: dependencies (topological order)
  4. For each scenario in that order, evaluates condition: (if present). A scenario without a condition always passes.
  5. Every scenario whose condition passes is enqueued into the scene's event chain — there is no first-match cut-off. Scenarios then execute one after another in enqueue order.

Priority therefore controls ordering, not selection: a lower-priority number means the scenario runs earlier in the chain, alongside all other passing scenarios.

Adding a custom action

Define an action class in your mod's src/:

public class OpenTreasureChestAction : IScenarioAction
{
    public string Name => "treasure.open";

    public void Run(IActionContext ctx)
    {
        var item = ctx.GetParam("item");
        var count = ctx.GetParam("count");
        ctx.Log("SCENARIO", $"Gave player {count}x {item}");
    }
}

IActionContext exposes GetParam(string) for reading action parameters plus the game subsystem services and Log/LogWarning methods (see Core/Actions/IActionContext.cs). There is no typed getter such as GetParamInt — parse values yourself.

Registration

You do not need to register actions manually: every implementation of IScenarioAction in your mod's compiled assembly is discovered automatically by reflection when the assembly is loaded.

If you need to register an assembly manually (outside the standard mod loading flow), call:

ScenarioActionFactory.Instance.RegisterAssembly(assembly);

If two actions register the same Name, the earliest registration wins and later duplicates are silently ignored.

Then use in scenarios:

action treasure.open item=food/ration count=5

${path} — Include Directive

Inside .scenario scripts and other mod text files, ${ path/to/file } is replaced with the full content of the referenced file at mod resolution time — before the script is ever parsed. Conditions — Quest Expression Language

Source: docs/mods/scenes/scenarios/dsl/conditions/index.md - https://cthangover.ru/docs/mods/scenes/scenarios/dsl/conditions/index

The condition: metadata field uses a simple expression language to control which scenarios execute based on quest state and scene flags. Boolean literals true and false are also valid condition expressions.

Syntax

condition: QuestId.method("arg") [&& || ! expr ...]

Available methods

MethodDescription
hasTag("tag")True if the quest has the specified tag
notHasTag("tag")True if the quest does NOT have the tag
IsActiveTrue when quest Status equals Progress
Status <op> NQuest status compared against number N
DataStatus <op> NQuest numeric counter compared against number N

Supported comparison operators (for both quest Status/DataStatus and flag comparisons): ==, !=, >, >=, <, <=.

Custom GDScript conditions

Mods can add custom condition names via GDScript. A GDScript with get_condition_name() + evaluate(flags, args) is auto-registered into the condition parser.

scripts/weather_conditions.gd:

extends RefCounted

func get_condition_name():
    return "gds.is_rain"

func evaluate(flags, args):
    return flags.get("weather", "") == "rain"

Usage in scenario:

condition: gds.is_rain

With arguments:

func get_condition_name():
    return "gds.flag_equals"

func evaluate(flags, args):
    var expected = args.get("0", "")
    return flags.get("custom_flag", "") == expected
condition: gds.flag_equals("victory")

GDScript conditions take priority over the built-in QuestParser — so gds.is_rain is resolved as a condition, not as a quest expression. See GDScript in Mods for details.

Flag conditions

Scene flags are evaluated directly — no scene. prefix needed:

condition: door_unlocked == "true"
condition: counter >= 3

Important: these flags are not fed by the DSL set command. set writes variables into the dialog runtime store, which are consumed by ${var} substitution and ctx.GetParam(...) in actions — a separate mechanism. The flag dictionary used here is populated via ScenarioCondition.SetFlag, which currently has no production callers. Do not expect set my_flag value to make condition: my_flag == "value" pass.

Operators

OperatorDescription
==, !=, >, >=, <, <=Comparison operators — valid for quest Status/DataStatus and flag comparisons

`\\`Logical OR — at least one side must be true
!Logical NOT — negates the following expression
()Grouping for precedence
true / falseBoolean literals

Real example — Murakami quest chain

scene: town_entry
priority: 20
condition: MeetingMurakamiQuest.hasTag("wolf_battle") && MeetingMurakamiQuest.notHasTag("boss_battle")
---
background "town/meetingmurakami/00002-1920617752"
text "[Wolf tracks lead straight to the doorstep]" key=meeting/after_wolf/tracks
# ... scenario continues ...

This scenario only fires after the player fought the wolf but before they fought the boss. It's the middle chapter of a three-part quest.

More complex examples

Multiple quest dependencies

condition: PrologQuest.hasTag("met_marao") && MeetingMurakamiQuest.hasTag("recruited")

Both conditions must be met.

Either/or branching

condition: PrologQuest.hasTag("found_book") || PrologQuest.hasTag("found_map")

Runs if the player found either the book OR the map.

Negation with OR

condition: !PrologQuest.hasTag("tutorial_done") && (PrologQuest.hasTag("woke_up") || PrologQuest.hasTag("in_alley"))

The tutorial hasn't been done yet, but the player has woken up or is in the alley.

Status-based progression

condition: PrologQuest.Status >= 2

Runs when PrologQuest reaches status 2 or higher.

Using DataStatus for numeric progress

condition: MainQuest.DataStatus >= 10

Runs when the quest's numeric progress counter reaches 10 or more.

Combining quest conditions with flags

condition: PrologQuest.hasTag("met_marao") && boss_battle == "done"

Runs when the prolog tag is set AND the scene flag boss_battle equals "done".

Condition evaluation order

  1. Engine collects all scenarios for the current scene
  2. Sorts by priority (ascending) and resolves after: dependencies
  3. Evaluates each scenario's condition: in that order; a scenario without a condition always passes
  4. All scenarios whose condition passes are enqueued into the event chain and run one after another — there is no first-match cut-off

This means:

  • Conditions filter scenarios out of the chain entirely; a passing scenario never blocks later scenarios from running
  • Priority only determines execution order among passing scenarios

    B["priority: 8<br/>condition: hasTag<br/>chapter_2"] -->|"fails"| X["Skipped"]
    C["priority: 10<br/>condition: none"] -->|"always passes"| S

Runtime TSCN Scene Loading

Source: docs/mods/scenes/tscn-runtime/index.md - https://cthangover.ru/docs/mods/scenes/tscn-runtime/index

Godot .tscn scene files can be loaded and instantiated at runtime — after the game is built — through a custom parser and builder. This is the primary mechanism for mods to ship pre-authored Godot scenes that are constructed identically to how Godot itself would build them.

Why a custom parser?

Godot's native PackedScene loading (ResourceLoader.Load<PackedScene>(path)) requires the scene to be present as a file on disk. Mods distributed as .zip archives cannot use this path. The custom parser reads .tscn text through IModFileProvider — the same abstract file backend that serves all other mod assets (textures, scenarios, JSON). This means scenes work identically whether the mod is a loose folder or a compressed archive.

    Builder --> NodeTree["Node tree"]

    Parser --> SecReg["SectionParser<br/>Registry"]

Entry point system

Any root node can declare an entry-point class via a special property:

[node name="MyScene" type="Control"]
__entry_point = "MyMod.EntryPointClass"

The class must implement ITscnSceneEntryPoint:

public interface ITscnSceneEntryPoint
{
    void OnSceneBuilt(Node sceneRoot);
}

The entry point is resolved across all loaded assemblies — mod-compiled code first, then Type.GetType(), then all AppDomain assemblies as fallback. OnSceneBuilt is called after the entire node tree is constructed, properties are applied, and signals are connected.

PackedScene resolution

When a node has instance=ExtResource("id"), the parser:

  1. Looks up the ext_resource by id to find the .tscn path
  2. Searches all mods in priority order for the file (same as script resolution)
  3. Recursively parses and builds the sub-scene
  4. Applies any override properties from the parent node (visible = false etc.)
; Parent scene
[ext_resource type="PackedScene" path="scenes/dialog.tscn" id="2_dialog"]
[node name="Dialog" parent="." instance=ExtResource("2_dialog")]
visible = false                    ; ← overwrites dialog.tscn root visibility

When a node property references a PackedScene (not via instance= but as an exported field):

answerBoxScene = ExtResource("2_answerbox")

The builder resolves it recursively, packs the result into a PackedScene via PackedScene.Pack(), and sets the property. This enables scripts with [Export] PackedScene fields to work identically to Godot's native loading.

Mod priority resolution

Both script paths and PackedScene paths are resolved through the mod priority system:

.tscn: path="scripts/MyScript.cs"
   → ScriptTypeRegistry: search all mods in load-order priority
   → First mod where the file exists (or the type is registered) wins

This is the same mechanism used by ModRegistry for asset deduplication. A mod with higher priority can override a scene dependency from another mod.

Mod Settings

Source: docs/mods/settings/index.md - https://cthangover.ru/docs/mods/settings/index

Mods can expose user-configurable settings that appear in the in-game settings menu under a dedicated "Mod Settings" tab. The UI shows a vertical list of mods (only those that have settings) on the left; clicking a mod name displays its settings controls on the right.

Architecture

The system mirrors the save system (IModSaveable) using a similar dispatch pattern:

Mod assembly loaded
  → ModSettingsRegistry.RegisterAssembly(assembly, modId)
    → Finds IModSettings implementation via reflection
    → Stores (modId, instance) pair

Boot time:
  → ModSettingsRegistry.LoadAll()
    → For each registered mod: load user://mod_settings/{modId}.json
    → Call mod.ReadValues(blob)

Settings menu opened:
  → ModSettingsRegistry.GetModsWithSettings()
    → Returns sorted list of mod IDs (only mods with IModSettings)
  → BuildModList() — creates buttons in left panel
  → On click: BuildModSettingsPanel(modId)
    → mod.GetDefinitions() → list of ModSettingDefinition
    → Creates UI controls (CheckButton, SpinBox, OptionButton, etc.)
    → mod.WriteValues(blob) → populates controls with current values

Setting changed:
  → Read all control values into DataBlob
  → ModSettingsRegistry.SaveModSettings(modId, blob)
  → ModSettingsRegistry.ApplyValues(modId, blob)
    → mod.ReadValues(blob) — immediate apply

Reset:
  → ModSettingsRegistry.DeleteModSettings(modId)
  → Rebuild panel with DefaultValues from definitions

Core concepts

IModSettings interface

Mods implement one class implementing IModSettings. It is auto-discovered when the mod assembly loads.

public interface IModSettings
{
    IReadOnlyList<ModSettingDefinition> GetDefinitions();
    void WriteValues(DataBlob blob);
    void ReadValues(DataBlob blob);
}
  • GetDefinitions() — Declares which settings the mod has. Called every time the settings panel opens.
  • WriteValues(blob) — The mod writes its current values into the blob. Called to populate UI controls and to persist.
  • ReadValues(blob) — The mod reads values from the blob and applies them. Called on boot (from persisted data) and on every UI change.

Schema changes

DataBlob.Version is NOT persisted for mod settings. ModSettingsRegistry.SaveModSettings writes only the key-value payload (blob.GetBytes()), and on load the registry constructs a fresh DataBlob(payload), which resets Version to its default of 1. (Version is persisted through the main save system's SavePackage — just not here.)

Detect schema changes by reading keys with defaults instead — missing keys resolve to your fallback values, so added fields need no migration logic:

public void WriteValues(DataBlob blob)
{
    blob.SetFloat("explosion_radius", _explosionRadius);
    blob.SetFloat("knockback_force", _knockbackForce); // added later
}

public void ReadValues(DataBlob blob)
{
    _explosionRadius = blob.GetFloat("explosion_radius", 1.5f);
    _knockbackForce = blob.GetFloat("knockback_force", 3.0f); // default for old saves
}

Important rules

  • One IModSettings per mod — create a single implementation in your assembly.
  • Always provide DefaultValue — used when no persisted value exists and on Reset.
  • Use DataBlob key-value API — GetInt/SetInt, GetFloat/SetFloat, GetString/SetString, GetBool/SetBool.
  • Always call with defaults — blob.GetInt("key", defaultVal) so missing keys don't break.
  • Key names are persistent — changing a Key creates a new setting; the old value is lost.
  • Provide localisation — add translations for all Name and Options values in locale/.
  • The version field in manifest.json is used by the save system for validation; mod settings have no persisted schema version (DataBlob.Version is reset to 1 on load) — handle schema changes via read-with-defaults.
  • Declare "sources" in manifest.json — your .cs files must be listed in the sources field of manifest.json for the compiler to pick them up. See Manifest — sources for details.

How shaders are referenced

Shaders are referenced by filename (no extension) in the engine. They can be:

  1. Assigned to materials in Godot scenes via the engine
  2. Overridden by mods — if a mod provides a shader with the same name, it replaces the default
  3. Applied to specific nodes via C# code, using the static Shaders facade

    (backed by ShaderResolver):

var shader = Shaders.Resolve("pixel_art");
if (shader != null)
{
    var material = node.Material as ShaderMaterial;
    material.Shader = shader;
}

The Shaders facade exposes:

  • Collect() — all .gdshader files across mods, keyed by logical name
  • Resolve(name) — loads the Shader resource by name (null if not found)
  • TryGetCached(name) — returns a previously resolved, still-valid instance

At runtime, ShaderModReplacer.PatchScene(Node) walks freshly instantiated scenes and swaps every ShaderMaterial whose original resource path matches a mod-provided shader name. The same pass also performs texture overrides: TextureRect and Sprite2D nodes have their textures matched by resource filename against the mod texture registry and replaced the same way — so PatchScene is not limited to shaders.

Engine-side consumers

The engine ships a dedicated Control node that consumes a mod-provided shader: PixelArtPostProcess (Core/Shaders/PixelArtPostProcess.cs). On _Ready it builds a full-viewport ColorRect, loads the pixel_art_post_process shader via the mod system, and exposes an [Export] float PixelSize property that drives the shader's pixel_size uniform — adjusting it from the Godot inspector updates the effect live.

Shipped core shaders

Besides the interface shaders listed above, the visual_novel_core mod ships its own shader family in mods/visual_novel_core/shaders/: a set of 2d_cubism_*.gdshader files (mask, mask_mul, mask_add, mask_mix — each also in an _inv inverted variant — plus norm_mul / norm_add / norm_mix) used for Cubism-style sprite masking and normal blending. Shader includes

.gdshaderinclude files can be shared across shaders:

shaders/noise_simplex.gdshaderinclude:

float simplex_noise(vec2 p) {
    // ... noise implementation ...
}

float fbm_noise(vec2 p, int octaves, float lacunarity, float gain) {
    float value = 0.0;
    float amplitude = 1.0;
    float frequency = 1.0;
    for (int i = 0; i < octaves; i++) {
        value += amplitude * simplex_noise(p * frequency);
        frequency *= lacunarity;
        amplitude *= gain;
    }
    return value;
}

Used in another shader:

    COLOR = vec4(n, n, n, 1.0);
}

C# Source Code in Mods

Source: docs/mods/src/index.md - https://cthangover.ru/docs/mods/src/index

Mods can include C# source files that are compiled at runtime via Roslyn. This allows mods to add new game mechanics, UI, battle systems, and scenario actions without modifying the kernel.

How it works

  1. Kernel discovers .cs files via manifest.json → "sources": ["src/**/*.cs"]
  2. Files are loaded as text, compiled via Roslyn into a separate assembly
  3. The assembly is loaded into the running game
  4. Types implementing known interfaces (IModInitializer, IBattleCore, IScenarioAction, etc.) are auto-discovered

What gets auto-registered from your assembly

Step 4 happens in ModAssemblyLoader.RegisterAssembly (Core/Mods/ModAssemblyLoader.cs) — the single point through which every new assembly enters the game. It fans out into every reflection-driven registry, so a public class implementing any of these is discovered without registration code:

ScriptTypeRegistry — resolving .tscn script paths

When a scene file references a script (path="..." in its headers), ScriptTypeRegistry (Core/Mods/ScriptTypeRegistry.cs) maps that path to the compiled System.Type inside the mod assembly, respecting mod load-order priority. It is populated by ModCompiler after each mod's C# compiles; ModRegistry.Initialize supplies the priority order via SetModOrder.

Only non-abstract classes deriving from Godot.Node are indexed — by class name, full name, and source file path. Paths are normalized before lookup (res:// prefix stripped, backslashes → forward slashes) and comparisons are case-insensitive.

Important: Godot input in mods

Because mod code compiles into a separate assembly (not processed by Godot's source generators), two rules apply:

  1. AddChild BEFORE GlobalPosition: If you set GlobalPosition before AddChild, the node has no parent canvas transform and the position will be misinterpreted.
// CORRECT
parent.AddChild(handle);
handle.GlobalPosition = target;

// WRONG
handle.GlobalPosition = target;
parent.AddChild(handle);
  1. Use GuiInput event instead of _GuiInput override: Due to Godot dispatch quirks between assemblies, subscribe to the C# event rather than overriding the virtual method:
public class MyHandle : ColorRect
{
    public MyHandle()
    {
        MouseFilter = Control.MouseFilterEnum.Stop;
        GuiInput += OnGuiInput;
    }

    private void OnGuiInput(InputEvent @event)
    {
        if (@event is InputEventMouseButton mb && mb.Pressed)
        {
            // handle click
            AcceptEvent();
        }
    }
}

Compilation errors

Roslyn compilation errors appear in the game log. Common issues:

  • Missing using directives — check namespace imports
  • Reference to non-existent APIs — verify the kernel version supports the method
  • Syntax errors — standard C# issues

The game will still run even if a mod's C# fails to compile. Non-C# assets (scenarios, items, etc.) from the same mod remain functional.

GDScript in Mods

Source: docs/mods/src/gdscript/index.md - https://cthangover.ru/docs/mods/src/gdscript/index

Mods can include .gd (GDScript) files alongside or instead of C# source code. GDScript files are compiled by Godot's built-in GDScript engine and can implement scenario actions, custom conditions, battle action executors, item actions, mod initializers, and winground listeners — all without Roslyn or a C# toolchain.

How it works

  1. Mod manifest declares "gd_sources": ["scripts/*.gd"]
  2. On mod load, the kernel finds .gd files, compiles them via GDScript.Reload(), instantiates, and inspects methods
  3. If the GDScript has known method patterns, it is auto-registered into the corresponding subsystem
  4. No manual registration code needed — the kernel does it automatically

manifest.json — gd_sources field

{
  "id": "my_mod",                                          // Canonical mod identifier
  "name": "My GDScript Mod",                               // Human-readable mod name
  "version": "1.0.0",                                      // Semver version
  "gd_sources": ["scripts/*.gd"],                          // Glob patterns for .gd files
  "depends": ["visual_novel_core"]                                      // Versioned dependency strings
}
FieldDescription
gd_sourcesGlob patterns for .gd files

Note on pattern matching: despite the glob-like syntax, the directory walk is always recursive. A pattern like scripts/*.gd is split at the last /: the part before it (scripts) selects the root directory, and the suffix after it (*.gd) only acts as a file name filter. As a result, scripts/*.gd also picks up files such as scripts/any/deep/foo.gd. There is no way to limit matching to a single directory level; use distinct top-level folders if you need separation.

A single .gd file can implement multiple interfaces simultaneously — the kernel checks all known patterns on each script.

Pages

  • Scenario Actions — actions + GDActionContext + service APIs
  • Custom Conditions — condition leaf parsers
  • Battle Action Executors — custom battle logic
  • Item Actions — item usage handlers
  • Mod Lifecycle — initializers, event bus, publishing events

Detection details:

  • Scenario actions are detected by the presence of get_name() together with run() — there is no separate get_action_name() convention.
  • Initializers register when either callback is present; each missing one is simply not invoked.
  • Winground listeners register only if get_winground_listener_id() returns a non-empty ID in addition to at least one hook method.

A single .gd file can implement multiple patterns simultaneously.

Order among C# and GDScript

  1. C# assemblies are compiled and loaded first (via Roslyn or precompiled DLLs)
  2. GDScript files are loaded second
  3. All registrations happen during the same load phase

GDScript conditions use RegisterFirst — they are inserted at the front of the leaf parser list, taking priority over the built-in QuestParser. This means gds.is_rain resolves before the parser tries to interpret gds as a quest ID.

Status Effects

Source: docs/mods/status_effects/index.md - https://cthangover.ru/docs/mods/status_effects/index

Status effects are temporary buffs, debuffs, or crowd-control effects applied to characters during battle. Defined as JSON data and managed through StatusEffectQueue on each character.

JSON structure

{
  // Unique status effect identifier — used to look up and apply effects
  "Id": "stun",
  // Locale key for the effect's display name in tooltips and the status panel
  "Name": "status/stun/name",
  // Locale key explaining what the effect does
  "Description": "status/stun/desc",
  // Effect category: "Buff" (positive), "Debuff" (negative), or "Stun" (skip turn)
  "Type": "Stun",
  // Number of turns the effect lasts before expiring
  "Duration": 2,
  // Behaviour set ID — resolved via StatusEffectActionFactory into IStatusActions
  "Actions": "stun",
  // Icon filename loaded from the characters mod group
  "Icon": "stun"
}

Field reference

FieldTypeDescription
IdstringUnique effect identifier
NamestringLocale key for display name (shown in tooltips and status panel)
DescriptionstringLocale key explaining what the effect does
Typestring"Buff", "Debuff", or "Stun"

Status effect types

TypeDescription
BuffPositive effect that benefits the bearer (e.g. stat boost, regeneration). Rendered with a friendly tint in the UI

Status effect index file

Status effects are registered via an index file:

{
  // $ref entries — ${stun} expands to status_effects/stun.json with its contents merged in
  "Items": [
    "${stun}"
  ]
}

Runtime behaviour

  • Each character has a StatusEffectQueue — an ordered list of active status effects
  • RemainingTurns decrements in both turn phases: in OnTurnStart (only for timed effects with Duration > 0) and unconditionally in OnTurnEnd
  • When RemainingTurns reaches 0, natural expiry fires OnFinalAction; manual removal via Remove() fires OnRemove instead
  • The battle engine checks HasStun() to skip a stunned character's turn
  • Effect behaviour callbacks are provided by IStatusActions, resolved from the Actions field via the factory

StatusEffectQueue API reference

The queue lives in Core/Battle/StatusEffect/StatusEffectQueue.cs (namespace Cthangover.Core.Cards.StatusEffect). It is attached per character as Character.StatusEffectQueue, created automatically in the Character constructor.

MemberDescription
ActiveStatusEffectsDefensive copy of the internal effect list (a new List per access) — safe to enumerate, external code cannot mutate the backing store
Add(string statusEffectId, int duration = -1)Resolves the ID via StatusEffectInfoFactory, constructs a StatusEffectItem, fires OnApply, and appends it. Returns false when the factory lookup fails. A positive duration overrides both Duration and RemainingTurns from the definition
Remove(string statusEffectId)Removes the first effect matching the ID, firing OnRemove first. Returns false if nothing matched
HasStun()true if any active effect has type Stun — checked by the battle engine to skip turns
OnTurnStart()Fires OnTurnStart on each effect, decrements RemainingTurns for timed effects (Duration > 0), and expires at zero via OnFinalAction
OnTurnEnd()Fires OnTurnEnd on each effect, decrements RemainingTurns unconditionally, removes expired effects via Remove (which also fires OnRemove)
OnDealDamage(Character target, ref int damage)Pipes outgoing damage through every effect's OnDealDamage hook, in insertion order
OnTakeDamage(Character source, ref int damage)Pipes incoming damage through every effect's OnTakeDamage hook
ClearAll()Fires OnRemove on each active effect, then clears the list
Copy(Character newOwner)Builds a new queue bound to newOwner; each effect is cloned via Copy() and OnApply is re-fired in the new owner's context

Timing semantics worth knowing:

  • IStatusEffect.Duration <= 0 means the effect never expires naturally — only Remove() or ClearAll() ends it
  • StatusEffectItem.RemainingTurns is tracked independently of the definition's Duration, so the original value survives for display or re-apply logic
  • StatusEffectItem.Copy() is a shallow clone: primitives are copied while the stateless Actions singleton is shared by reference

Built-in behaviour sets live under Core/Battle/StatusEffect/Impls/ — e.g. StunStatusEffect (ID = "basic/stun") implements every IStatusActions hook as a no-op, because stun is detected via HasStun() rather than through action callbacks.

Implementing custom status effect behaviour

Create an IStatusActions implementation. Registration is fully automatic: the StatusEffectActionFactory constructor calls Reflections.FindAndCreate<IStatusActions>(), and mod assemblies are scanned by ModAssemblyLoader — no manual registration is needed:

public class PoisonStatusActions : IStatusActions
{
    // Mandatory factory key matching the JSON "Actions" field (e.g. "basic/stun")
    public string ID => "basic/poison";

    public void OnApply(Character target) { /* called when effect is applied */ }
    public void OnTurnStart(Character target) { /* start-of-turn tick: DoT, regen */ }
    public void OnTurnEnd(Character target) { /* end-of-turn hook */ }
    public void OnDealDamage(Character source, Character target, ref int damage) { /* amplify/reduce outgoing damage */ }
    public void OnTakeDamage(Character target, Character source, ref int damage) { /* amplify/reduce incoming damage */ }
    public void OnRemove(Character target) { /* manual removal (cleanse) */ }
    public void OnFinalAction(Character target) { /* natural expiry */ }
    public void ModifyAttributes(CharacterAttributes attributes) { /* passive stat modifier */ }
}

Tools bootstrapping happens at startup:

Abstract base class for tool popup windows. Extends Godot's Window. Key features:

    maximized fills the game viewport, restore returns to the previous geometry.

Wrappers — UI Templates

Source: docs/mods/wrappers/index.md - https://cthangover.ru/docs/mods/wrappers/index

Wrapper templates (.wrappertmpl) define how mod UI is built inside a scene. A wrapper template is not JSON — it is a C# source file that is compiled at runtime, with your subscription's code fragment substituted into it.

Directory structure

wrappers/
├── default.wrappertmpl
└── custom_layout.wrappertmpl

What wrappers do

When a mod subscribes to a scene (manifest.json → subscriptions), the template field selects which wrapper template to compile and run:

{
  "subscriptions": [
    {
      "scene": "home_kitchen",       // Target scene ID
      "template": "default",         // Wrapper template name (from wrappers/ directory) — MANDATORY
      "code": "cooking_panel_init",  // File name of the C# fragment loaded from subscriptions/{code}.cs
      "trigger": "on_enter",         // Lifecycle event: on_enter | on_exit
      "priority": 10                 // Execution order: lower runs earlier among multiple subscribers
    }
  ]
}

Subscription entry fields:

  • scene — target scene ID
  • template — wrapper template path/name (mandatory: if missing, the whole subscription entry is skipped as invalid)
  • code — file name of the C# fragment loaded from subscriptions/{code}.cs (names a file, not a class)
  • trigger — "on_enter" / "on_exit", defaults to "on_enter"
  • priority — defaults to 10; subscriptions with a lower priority value run first

The "template": "default" means the cooking UI code runs inside the default wrapper template.

Real example — visual_novel_core/wrappers/default.wrappertmpl

A wrapper template is plain C# source defining a static class named SceneBuilderScript with a few helper methods and a Run(Node root) method containing the {{USER_CODE}} substitution marker:

using Godot;
using System;
using System.Linq;
using System.Collections.Generic;

public static class SceneBuilderScript
{
    private static Node _root;

    public static T Get<T>(string name) where T : Node
    {
        return _root.GetNode<T>(name);
    }

    public static Node Get(string name)
    {
        return _root.GetNode(name);
    }

    public static T FindNode<T>(string nodeName) where T : Node
    {
        return Cthangover.Core.Scenes.SceneContextNode.FindNode<T>(nodeName);
    }

    public static void Run(Node root)
    {
        _root = root;
        {{USER_CODE}}
    }
}

When the trigger fires, the template text is taken, the {{USER_CODE}} marker is replaced with your subscription's C# fragment (the contents of subscriptions/{code}.cs), the result is compiled via Roslyn, and SceneBuilderScript.Run(root) is invoked via reflection with the scene root node. Compilation results are cached per template+code pair for reuse across scene visits.

In your subscription code fragment, you can use the template's helpers to find UI containers by name and build your UI:

var modPanel = FindNode<Control>("Lastground");
if (modPanel == null)
    return;

var myPanel = new MyUIPanel();
myPanel.Name = "MyCustomPanel";
modPanel.AddChild(myPanel);

Creating a custom wrapper

wrappers/side_panel.wrappertmpl — any C# class named SceneBuilderScript with a Run(Node root) method works; include whichever helpers your fragments need:

using Godot;

public static class SceneBuilderScript
{
    public static void Run(Node root)
    {
        // Your subscription's code fragment replaces this marker:
        {{USER_CODE}}
    }
}

Then reference it in your manifest:

{ "scene": "my_scene", "template": "side_panel", "code": "my_handler" }  // Uses side_panel template

Remember: template is mandatory — an entry without it will not be registered at all.

Execution order

On scene enter, event bus subscribers run in priority order:

  1. Priority 15 — [SceneEvent]-composed chain events run (SceneManager.ComposeEvents, combining .scenario definitions and [SceneEvent] classes)
  2. Priority 20 — manifest subscriptions execute (SceneSubscriptionRegistry)

Among subscriptions themselves, those with a lower priority value run first.

Using ModWidget

When creating UI components from mod C# code, inherit from ModWidget (Core/UI/Base/Lists/ModWidget.cs). It provides an idempotent Construct()/Destruct() lifecycle for UI built from code inside mods: EnsureConstructed() calls the abstract Construct() exactly once, and the virtual Destruct() is called automatically on _ExitTree. Usage = override Construct() and build your children there:

public class MyUIPanel : ModWidget
{
    protected override void Construct()
    {
        var label = new Label { Text = "Hello from mod!" };
        AddChild(label);
    }
}

Call EnsureConstructed() before adding the widget to the tree (as CardBattleCore does), so its children are constructed exactly once regardless of how many times construction is requested.

Mod Packaging — .zip Distribution

Source: docs/mods/zip/index.md - https://cthangover.ru/docs/mods/zip/index

Mods can be distributed as .zip archives instead of loose folders. The kernel loads them identically — zip is just a transport format.

When to use .zip vs folder

FormatUse case
FolderLocal development. Instant iteration — edit files, reload game
.zipDistribution. Share with players, upload to mod platforms, versioned releases

Directory structure inside the zip

The zip must have the same structure as a loose mod folder:

my_mod.zip/
├── manifest.json
├── src/
│   └── MyCode.cs
├── scenarios/
│   └── my_scene.scenario
├── items/
│   └── items.json
├── backgrounds/
│   └── my_bg.png
├── locale/
│   └── en.properties
└── ...                     # any other assets

The root of the zip IS the mod root — no extra wrapper folder.

How the kernel loads zipped mods

  1. On startup, the registered mod scanners (UserDataModScanner and GameDirModScanner) enumerate filesystem entries in their respective mods/ directories — both folders and .zip files are returned as DiscoveredModEntry items
  2. The ZipModLoader claims any entry path ending with .zip and creates a ZipModFileProvider — the archive is opened directly with ZipFile.OpenRead, building an O(1) entry lookup dictionary in memory without extracting files to disk
  3. The mod is loaded as if it were a folder — manifest.json is read from inside the zip, sources compiled, assets discovered
  4. Zip mods have the same dependency resolution and lifecycle as folder mods; deduplication priority is controlled by the scanner's ModSourceRoot.Priority, not by format type

See Resources — Loaders for details on how ZipModLoader and custom loaders work.

Creating a .zip for distribution

From the mod's parent directory:

# From mods/
zip -r my_mod_v1.0.0.zip my_mod/

Or using the Python build script (add this to your mod's tooling):

import shutil
import json

def pack_mod(mod_path, output_path):
    with open(f"{mod_path}/manifest.json") as f:
        manifest = json.load(f)

    name = manifest.get("name", mod_path)
    version = manifest.get("version", "0.0.0")
    archive = f"{output_path}/{name}_v{version}"

    shutil.make_archive(archive, "zip", mod_path)
    print(f"Packed: {archive}.zip")

Testing a zipped mod

  1. Place the .zip in mods/
  2. Remove the source folder (or keep both — if both a folder and a zip share the same mod ID, only one loads: a higher version always wins regardless of enumeration order; when versions are equal the first-encountered entry wins within the same root priority, and a lower-priority root always loses)
  3. Launch the game — the mod loads from the zip
  4. Check the game log for any errors

Mod versioning

Include a version field in manifest.json for proper version tracking:

{
  "name": "MyMod",                                         // Human-readable mod name
  "version": "1.2.0",                                      // Semver version for tracking and compatibility
  "author": "you",                                         // Author credit
  "description": "..."                                     // Short description of the mod
}

The kernel does enforce version deduplication — ModRegistry.RegisterCandidates() keys candidates by mod Id, so only one version of a given mod ever loads:

  • Within the same root priority: a candidate with a higher version replaces the already-registered one (logged as a warning); an equal or lower version is skipped with a warning — for equal versions, first-encountered wins.
  • A candidate from a lower-priority root never replaces one from a higher-priority source, regardless of version.

Use version numbers for player information and mod platform compatibility checks.

Zip mod limitations

  • No hot-reload: Editing files inside a zip requires repacking. Use folders during development
  • No filesystem paths: GetFileSystemPath() always returns null for zip mods — Godot's ResourceLoader cannot load scenes or shaders directly from within a zip. Assets that require filesystem access (shaders, scenes) are extracted to the mod cache on demand
  • File size: No hard limit on zip size, but the entry lookup dictionary grows linearly with the number of files — very large archives (>10,000 entries) may increase the initial dictionary build time

Resources — Pluggable Mod Infrastructure

Source: docs/resources/index.md - https://cthangover.ru/docs/resources/index

The kernel's resource pipeline is built on a strategy pattern that lets mods extend how mods are discovered, where they come from, and how they are read. This page gives an overview; each subsection covers one layer in detail.

Architecture

Three layers work together to turn a URL or folder path into a loaded mod:

Scanner (IModScanner)          "I know where mods live"
    ↓
Loader  (IModLoader)           "I know how to open this kind of mod"
    ↓
Provider (IModFileProvider)    "I provide file access to a loaded mod"

Scanners and loaders are discovered automatically via Reflections.FindAndCreate<T>() and registered with ModDiscoveryRegistry — any public, non-abstract class implementing the interface with a parameterless constructor is picked up at startup. Mod DLLs can ship their own scanners/loaders; they are registered when the mod assembly is loaded and take priority over built-in ones via LIFO lookup.

Providers are not part of this registry — there is no provider registry. Each loader constructs its provider directly: FolderModLoader creates a FolderModFileProvider, ZipModLoader creates a ZipModFileProvider. To supply custom storage (memory, network, database), a mod ships its own IModLoader whose CreateProvider() returns the custom IModFileProvider.

Layers at a Glance

LayerInterfaceBuilt-in implementationsWhat mods can add
ProvidersIModFileProviderFolderModFileProvider, ZipModFileProviderCustom storage backends — shipped as an IModLoader that constructs them in CreateProvider() (see Loaders)
ScannersIModScannerUserDataModScanner, GameDirModScannerNew mod sources (HTTP catalog, Steam Workshop, Git repos)
LoadersIModLoaderFolderModLoader, ZipModLoaderNew mod formats (.7z, .tar.gz, remote zip download)

How a mod adds a custom scanner — quick example

A mod that wants to load mods from an HTTP catalog ships one class:

using System.Collections.Generic;
using Cthangover.Core.Mods.Discovery;

namespace MyMod
{
    public class HttpCatalogScanner : IModScanner
    {
        public string Name => "HTTP Catalog";

        public bool IsCanProvide(string url)
        {
            return url.StartsWith("https://");
        }

        public IEnumerable<ModSourceRoot> GetRoots()
        {
            yield return new ModSourceRoot
            {
                Url = "https://catalog.example.com/mods",
                Priority = 10
            };
        }

        public IEnumerable<DiscoveredModEntry> Discover(string rootUrl)
        {
            // HTTP GET rootUrl, parse JSON array of mod URLs,
            // yield return new DiscoveredModEntry { ... } for each
        }
    }
}

No registration code needed — Reflections.FindAndCreate<IModScanner>() finds it automatically when the mod's assembly is loaded.

Priority and LIFO lookup

  • Root priority (ModSourceRoot.Priority): lower number = higher precedence in deduplication. UserDataModScanner uses 0 (user mods win), GameDirModScanner uses 1 (built-in mods are overridden).
  • LIFO lookup (scanners/loaders): the last-registered scanner or loader that says IsCanProvide(url) == true wins. Since mod-added implementations are registered after built-in ones, they are checked first and can override core behaviour. This applies only to scanners and loaders — providers are never looked up, they are constructed by their loader.

Discovery Registry — `ModDiscoveryRegistry`

Source: docs/resources/discovery-registry/index.md - https://cthangover.ru/docs/resources/discovery-registry/index

The central registry that auto-discovers all IModScanner and IModLoader implementations and provides LIFO-ordered lookup. There is exactly one instance — a static singleton initialised once by ModRegistry.Initialize().

Discovery

At startup, Reflections.FindAndCreate<T>() scans all loaded assemblies for public, non-abstract classes implementing IModScanner or IModLoader with a parameterless constructor. Initialize() is idempotent — an _initialized guard makes repeated calls no-ops:

public static void Initialize()
{
    if (_initialized)
        return;
    _initialized = true;

    _scanners.AddRange(Reflections.FindAndCreate<IModScanner>());
    _loaders.AddRange(Reflections.FindAndCreate<IModLoader>());
}

When a mod assembly is loaded, ModAssemblyLoader.RegisterAssembly() fans out to ModDiscoveryRegistry.RegisterAssembly(), which runs the same discovery on the new assembly — appending any found scanners/loaders to the end of the registration lists.

LIFO lookup

Both FindScanner(url) and FindLoader(url) walk the registration list from the end (last-registered first). This gives mod-added providers priority over built-in ones:

public static IModLoader FindLoader(string url)
{
    for (int i = _loaders.Count - 1; i >= 0; i--)
        if (_loaders[i].IsCanProvide(url))
            return _loaders[i];
    return null;
}

Registration order (typical)

StepRegisteredOrder in list
Core assembly initUserDataModScanner, GameDirModScannerfirst
Core assembly initFolderModLoader, ZipModLoaderfirst
Mod A loadedCommunityCatalogScannerEnd → checked first
Mod B loadedHttpZipLoaderEnd → checked first

Exact index positions of the built-in scanners/loaders are not guaranteed — the order within a single assembly comes from the assembly/type enumeration performed by Reflections.FindAndCreate<T>(). The only reliable property is relative order: mod-added implementations are always appended after built-in ones, and LIFO lookup walks from the end.

After Mod A and Mod B load:

  • FindLoader("https://example.com/mods/cool.zip") → HttpZipLoader (last, checked first) ✓
  • FindLoader("C:/mods/cool") → FolderModLoader (only built-in matching)
  • FindScanner("https://catalog.example.com/mods") → CommunityCatalogScanner ✓

Public API

public static class ModDiscoveryRegistry
{
    // All registered scanners/loaders in registration order
    public static IReadOnlyList<IModScanner> Scanners { get; }
    public static IReadOnlyList<IModLoader> Loaders { get; }

    // Idempotent init — scans assemblies for implementations
    public static void Initialize();

    // Called by ModAssemblyLoader when a mod DLL loads
    public static void RegisterAssembly(Assembly assembly);

    // LIFO search — returns first matching provider or null
    public static IModScanner FindScanner(string url);
    public static IModLoader FindLoader(string url);
}

How ModRegistry uses the registry

The full discovery flow in ModRegistry.Initialize():

// 1. Discover all scanners and loaders
ModDiscoveryRegistry.Initialize();

// 2. For each scanner, enumerate its roots
foreach (var scanner in ModDiscoveryRegistry.Scanners)
{
    foreach (var root in scanner.GetRoots())
    {
        if (!scanner.IsCanProvide(root.Url))
            continue;  // Root not accessible — skip

        // 3. For each discovered entry, find a loader
        foreach (var entry in scanner.Discover(root.Url))
        {
            // Entries named ".gdignore" / ".gitkeep" are skipped
            var loader = ModDiscoveryRegistry.FindLoader(entry.Url);
            if (loader == null)
                continue;  // No loader claims this entry

            // 4. Create provider, read manifest, build candidate
            var provider = loader.CreateProvider(entry.Url, entry.EntryName);
            var manifest = ReadManifest(provider);
            // ... register candidate for deduplication ...
        }
    }
}

Deduplication happens afterwards in ModRegistry.RegisterCandidates(): candidates are keyed by mod Id, compared first by root priority (lower wins), then by version (higher version wins). See Load order and the zip packaging page for details.

Loaders — `IModLoader`

Source: docs/resources/loaders/index.md - https://cthangover.ru/docs/resources/loaders/index

A loader takes a single mod entry URL (returned by a scanner's Discover()) and creates the IModFileProvider that gives file access to that mod. It also provides the fallback mod ID used when manifest.json has no id field.

Loaders are matched to entries via IsCanProvide(url) — the first loader that says "I can handle this" (in LIFO order) gets to create the provider.

Base interface — IModDiscoveryProvider

Both IModLoader and IModScanner extend a common base, IModDiscoveryProvider (Core/Mods/Discovery/IModDiscoveryProvider.cs):

public interface IModDiscoveryProvider
{
    string Name { get; }                // Human-readable name for log messages ("Folder", "Zip", ...)
    bool IsCanProvide(string url);      // Can this provider handle the given path or URL?
}

The shared contract is what lets ModDiscoveryRegistry discover both kinds of providers via Reflections.FindAndCreate and apply the same LIFO lookup semantics: the last-registered provider that answers true to IsCanProvide wins. For loaders IsCanProvide is a type-dispatch check (is it a folder? a zip?); for scanners it acts as an accessibility guard (does the directory exist?).

Interface

public interface IModLoader : IModDiscoveryProvider
{
    string Name { get; }                                          // "Folder", "Zip", "HTTP Download", ...
    bool IsCanProvide(string url);                                // Type-dispatch: is it a folder? a zip?
    IModFileProvider CreateProvider(string url, string modName);  // Create the file provider
    string GetFallbackModId(string url, string entryName);        // ID when manifest has no id field
}

Built-in loaders

FolderModLoader

Claims any path that Directory.Exists() returns true for. Creates a FolderModFileProvider — the only provider type that supports Godot scene instantiation.

MethodBehaviour
IsCanProvide(url)Directory.Exists(url)
CreateProvider(url, modName)new FolderModFileProvider(url, modName)
GetFallbackModId(url, entryName)Returns entryName unchanged

ZipModLoader

Claims any path ending with .zip (case-insensitive). Creates a ZipModFileProvider that opens the archive and builds an O(1) entry lookup.

MethodBehaviour
IsCanProvide(url)url.EndsWith(".zip", OrdinalIgnoreCase)
CreateProvider(url, modName)new ZipModFileProvider(url, modName)
GetFallbackModId(url, entryName)Path.GetFileNameWithoutExtension(entryName) — strips the .zip extension

Loader matching order

Loaders are checked LIFO (last-registered first). This means:

  • Built-in loaders are registered first (Folder, then Zip)
  • Mod-added loaders are registered later and checked before built-ins
  • A mod can override ZipModLoader with its own zip handler by claiming .zip paths first

The kernel checks for a matching loader like this:

var loader = ModDiscoveryRegistry.FindLoader(entry.Url);  // LIFO search
if (loader == null)
    return;  // skip this entry — no loader claims it

var fileProvider = loader.CreateProvider(entry.Url, entry.EntryName);
var manifest = ReadManifest(fileProvider);
var id = manifest.Id ?? loader.GetFallbackModId(entry.Url, entry.EntryName);

Adding a custom loader via a mod

A loader that downloads and opens a remote zip:

using System;
using System.IO;
using System.Net.Http;
using Cthangover.Core.Mods;
using Cthangover.Core.Mods.Discovery;
using Cthangover.Core.Mods.Providers;

namespace MyMod
{
    public class HttpZipLoader : IModLoader
    {
        public string Name => "HTTP Zip";

        public bool IsCanProvide(string url)
        {
            return url.StartsWith("https://") && url.EndsWith(".zip");
        }

        public IModFileProvider CreateProvider(string url, string modName)
        {
            using var client = new HttpClient();
            var bytes = client.GetByteArrayAsync(url).Result;

            var tempPath = Path.Combine(Path.GetTempPath(), $"{modName}.zip");
            File.WriteAllBytes(tempPath, bytes);

            return new ZipModFileProvider(tempPath, modName);
        }

        public string GetFallbackModId(string url, string entryName)
        {
            return Path.GetFileNameWithoutExtension(entryName);
        }
    }
}

Paired with the CommunityCatalogScanner from the Scanners page, you now have a complete HTTP mod pipeline: scanner discovers URLs → loader downloads and opens zips → ZipModFileProvider provides file access.

Providers — `IModFileProvider`

Source: docs/resources/providers/index.md - https://cthangover.ru/docs/resources/providers/index

A provider is the bottom layer of the resource pipeline. It gives read-only access to a single mod's files — text, binary, streams, directory listings — without the rest of the engine knowing whether those files come from a folder on disk, a .zip archive, or something else entirely.

Interface

public interface IModFileProvider : IDisposable
{
    string Mod { get; }                          // Short mod name for logging
    string RootPath { get; }                     // Path to the mod's root storage (folder or zip file)

    bool FileExists(string path);                // Check if a file exists
    IEnumerable<string> ListFiles(string directory = "");  // Shallow listing; dirs end with /
    string ReadFileText(string path);            // Read UTF-8 text, or null
    byte[] ReadFileBinary(string path);          // Read binary, or null
    Stream OpenStream(string path);              // Open a seekable stream
    string GetFileSystemPath(string path);       // Absolute path, or null (missing file / non-filesystem provider)
    string ResolveIncludePath(string includePath, string currentPath);  // Resolve relative includes
}

IDisposable is required because zip-based providers hold native OS file handles that must be released on mod unload. Folder providers implement Dispose as a no-op.

Built-in providers

FolderModFileProvider

Backed by a real directory on disk. This is the only provider type that supports GetFileSystemPath returning a non-null value — which means it is the only type that can serve Godot scenes via ResourceLoader and PackedScene instantiation.

var provider = new FolderModFileProvider("mods/my_mod", "my_mod");
string text = provider.ReadFileText("manifest.json");
string fsPath = provider.GetFileSystemPath("scenes/battle.tscn");  // absolute path

Note that GetFileSystemPath returns null when the file does not exist — not just for non-filesystem providers. Callers must handle the null return for missing files as well.

ZipModFileProvider

Backed by a .zip archive. On construction the entire entry table is flattened into a case-insensitive dictionary for O(1) lookups. ListFiles simulates directory listing by grouping flat zip entries.

var provider = new ZipModFileProvider("mods/my_mod.zip", "my_mod");
string text = provider.ReadFileText("manifest.json");
string fsPath = provider.GetFileSystemPath("scenes/battle.tscn");  // always null

Limitations:

  • GetFileSystemPath always returns null — Godot cannot load resources from inside a zip
  • Callers that need scene instantiation must extract assets to the cache first (ModCacheManager)
  • The zip stays open until Dispose() is called

Scanners — `IModScanner`

Source: docs/resources/scanners/index.md - https://cthangover.ru/docs/resources/scanners/index

A scanner knows about a source of mods — a directory on disk, an HTTP catalog, a Steam Workshop subscription folder, or a Git repository. Each scanner declares its root URLs via GetRoots() and enumerates available mods via Discover().

This replaces the old hardcoded ResolveModsRoots() method. Instead of the kernel knowing about user://mods/ and res://mods/, each scanner declares its own roots.

Interface

public interface IModScanner : IModDiscoveryProvider
{
    string Name { get; }                          // "UserData", "GameDir", "HTTP Catalog", ...
    bool IsCanProvide(string url);                // Accessibility guard — does the root exist?
    IEnumerable<ModSourceRoot> GetRoots();        // Roots this scanner knows about, with priorities
    IEnumerable<DiscoveredModEntry> Discover(string rootUrl);  // Enumerate mods at a root
}

IsCanProvide — the accessibility guard

Scanners always return their potential roots from GetRoots(). IsCanProvide acts as a filter — it is called on each root before discovery, and roots where it returns false are silently skipped. For filesystem scanners this means Directory.Exists(url); for HTTP scanners it could mean a ping or health check.

This pattern avoids calling Godot APIs outside the runtime. When GameEnvironment.IsRuntime is false (editor, tests), the scanner returns a raw Godot path like "user://mods/" — Directory.Exists("user://mods/") returns false, so the root is skipped without ever touching ProjectSettings.GlobalizePath.

ModSourceRoot

Each root carries a deduplication priority:

public class ModSourceRoot
{
    public string Url { get; set; }      // Filesystem path or URL
    public int Priority { get; set; }    // Lower = higher precedence in dedup
}

DiscoveredModEntry

public class DiscoveredModEntry

Adding a custom scanner via a mod

A mod that publishes a community catalog over HTTP:

using System.Collections.Generic;
using System.Net.Http;
using System.Text.Json;
using Cthangover.Core.Mods.Discovery;

namespace CommunityCatalog
{
    public class CommunityCatalogScanner : IModScanner
    {
        private const string CatalogUrl = "https://community.example.com/catalog.json";

        public string Name => "Community Catalog";

        public bool IsCanProvide(string url)
        {
            // Check if server is reachable
            try
            {
                using var client = new HttpClient { Timeout = TimeSpan.FromSeconds(3) };
                var response = client.Send(new HttpRequestMessage(HttpMethod.Head, url));
                return response.IsSuccessStatusCode;
            }
            catch
            {
                return false;
            }
        }

        public IEnumerable<ModSourceRoot> GetRoots()
        {
            yield return new ModSourceRoot
            {
                Url = CatalogUrl,
                Priority = 10  // Lower priority than local mods
            };
        }

        public IEnumerable<DiscoveredModEntry> Discover(string rootUrl)
        {
            using var client = new HttpClient();
            var json = client.GetStringAsync(rootUrl).Result;
            var entries = JsonSerializer.Deserialize<List<CatalogEntry>>(json);

            foreach (var entry in entries)
            {
                yield return new DiscoveredModEntry
                {
                    Url = entry.DownloadUrl,
                    EntryName = entry.Name
                };
            }
        }

        private class CatalogEntry
        {
            public string Name { get; set; }
            public string DownloadUrl { get; set; }
        }
    }
}

Drop this class in a mod DLL with "sources": ["src/CommunityCatalogScanner.cs"] in manifest.json — the kernel discovers it automatically.

You will also need a custom loader that knows how to download and open the zip files returned by this scanner. See Loaders.

Level 2 — Modder: DSL Scene

Source: quickstart/en/modder.md - https://cthangover.ru/quickstart/en/modder

JSON + DSL
15 minutes
No code

You'll create a mod with your own scene — a room with dialogue, choices, and transitions. And you'll add a "Go to the tavern" option to the existing kitchen scene without touching the original files.

Step 1: Mod structure

Create the folder and base files:

mods/
└── quickstart_modder/
    ├── manifest.json
    ├── scenes/
    │   └── my_alko_bar.json              # Our new location — the booze bar!
    ├── scenarios/
    │   ├── my_alko_bar.scenario          # Scenario inside the bar, let the player interact with the new location
    │   └── town_entry_override.scenario  # Override the town scene to add a transition to our new location
    ├── backgrounds/
    │   └── my_alko_bar/
    │       └── bg.png                    # Bar interior image
    ├── backgrounds/
    │   └── sounds/
    │       └── alko_bar_ambient.ogg      # Background bar noise sound
    └── locale/
        └── ru.properties                 # Localization for Russian

Step 2: manifest.json

mods/quickstart_modder/manifest.json:

{
  "id": "alko_bar",                                    // Mod ID
  "name": "My Booze Bar",                              // Mod name shown in the mod menu
  "description": "Adds a booze bar scene to the town", // Mod description shown in the mod menu
  "author": "modder",                                  // Mod author
  "depends": ["visual_novel_core"]                                  // Dependency on the core game (so manual mod load ordering is not required)
}

Step 3: Scene definition

mods/quickstart_modder/scenes/my_alko_bar.json:

{
  "name": "my_alko_bar",                              // Create a new, unique scene identifier (used in switch_scene), this will be the new scene.
  "defaultBackground": "my_alko_bar/bg",              // Path to the PNG background inside backgrounds/ (without extension)
  "defaultAmbient": "locations/alkobar/bar_ambient",  // ID of the ambient sound for this location (without extension), e.g. "bar noise" that plays on entering the scene
  "defaultScenario": "scenarios/my_alko_bar.scenario" // Default scenario that will run in this scene if nothing else is specified
}
FieldDescription
nameUnique scene ID. Used in switch_scene
defaultBackgroundPath to background inside backgrounds/ (no extension)
defaultAmbientAmbient sound. Empty string — no sound
defaultScenarioPath to the .scenario file that runs on scene entry

Step 4: Background

Place an image at mods/quickstart_modder/backgrounds/my_alko_bar/bg.png.

Any PNG image will work. The game supports shader-based lighting and time of day — the background will be automatically lit.

If you don't have an image, temporarily copy mods/visual_novel_core/backgrounds/home/kitchen.png → mods/quickstart_modder/backgrounds/my_alko_bar/bg.png.

Step 5: DSL Scenario

mods/quickstart_modder/scenarios/my_alko_bar.scenario:

scene: my_alko_bar
priority: 10
---
text "You walk into a half-empty bar."
text "A bored bartender stands behind the counter."

select "[What will you do?]"
option "Approach the counter" -> :bar
option "Leave" -> :leave

:bar
text "The bartender nods at you."
text "— What can I get you?"
end

:leave
switch_scene town_entry
end

What's happening here

  • text — displays a line of dialogue. The key= parameter is a localization key.
  • select — opens a choice menu. The text in quotes is the prompt.
  • option — a choice option. -> :label — where to jump when selected.
  • :bar, :leave — labels for jumps.
  • switch_scene — moves the player to another scene.
  • end — ends the scenario (player stays in the scene).

Step 6: Extending the town (scene priority)

Now let's add a "Go to the bar" option to the town scene, without touching the original visual_novel_core file.

mods/quickstart_modder/scenarios/town_entry_override.scenario:

scene: town_entry
priority: 1
---
select "The town smells different today..."
option "Go back home" -> :home
option "Go to the bar" -> :alko_bar

:home
switch_scene home_outside
end

:alko_bar
switch_scene my_alko_bar
end

Why this works

The town_entry scene now has two scenarios:

  • priority: 10 — default (from the visual_novel_core mod)
  • priority: 1 — ours (from quickstart_modder)

The engine runs the scenario with the lowest priority. Our priority: 1 wins — the player sees the new option.

Learn more: Scene Priority System.

Step 7: Check it

Start the game:

  1. Enter the town — you see the "Go to the bar" option.
  2. Click it — you're in your my_alko_bar scene with dialogue and choices.
  3. Choose "Leave" — you return to the town.

Level 1 — Player: Patching a Character

Source: quickstart/en/player.md - https://cthangover.ru/quickstart/en/player

Text editor
5 minutes
No code

You'll buff the character Marao — increase health, attack, and add the "Stun" ability — using the patch system. Zero code, just JSON.

Step 1: Create the mod folder

Every mod lives in its own folder inside mods/. Create:

mods/
└── quickstart_player/
    ├── manifest.json
    └── patches/
        └── characters.json

Step 2: manifest.json

Every mod needs a manifest. Create mods/quickstart_player/manifest.json:

{
  "id": "quickstart_player",        // Unique mod identifier, use English
  "name": "Marao Buff",             // Display name shown in the mod management menu
  "description": "My first mod!",   // Description visible in the mod list and catalog
  "author": "player",               // Mod author (arbitrary string)
  "depends": ["visual_novel_core"]               // Dependency on the core game (so manual mod load ordering is not required)
}

A minimal manifest only needs name, but it's better to fill in id as well. The kernel auto-discovers the folder and loads it as a mod.

Step 3: Character patch

Create mods/quickstart_player/patches/characters.json:

{
  "Items": [
    {
      "Id": "Marao", // Character ID to patch (defined in the core mod)

      "Health": 5000, // New property values — overwrite the originals
      "Attack": 1200,
      "Points": 2,

      "Actions$add": ["physics/stun"] // $add appends elements to an array
    }
  ]
}

How it works

  • "Id": "Marao" — the patch target: character with identifier Marao (defined in the visual_novel_core mod).
  • "Health": 5000, "Attack": 1200, "Points": 2 — overwrite the character's fields. New values replace old ones.
  • "Actions$add": ["physics/stun"] — the $add suffix means "append to the array". The action physics/stun is added to the list. The default physics/attack and physics/defence remain.

Learn more about patches: Patches and Array Operations.

Step 4: Run and check

Start the game. Enter any battle — Marao now has:

  • 5000 HP instead of 10
  • 1200 ATK instead of 5
  • 2 AP instead of 1
  • A third action "Stun" alongside "Attack" and "Defence"

Step 2: manifest.json

mods/quickstart_programmer/manifest.json:

{
  "id": "quickstart_programmer",                // Mod ID
  "name": "My Code Mod",                        // Mod name shown in the mod list
  "description": "New action and mod settings", // Mod description shown in the mod list
  "sources": ["src/*.cs"],                      // Glob pattern for collecting source files (include all ".cs" files)
  "author": "programmer",                       // Author
  "depends": ["visual_novel_core"]                           // Dependency on the core game (so manual mod load ordering is not required)

The sources field specifies which C# files to compile via Roslyn.

Step 3: Entry point — IMod

mods/quickstart_programmer/src/MyMod.cs:

using Cthangover.Core.Mods;
using Cthangover.Core.Utils;
using Godot;

namespace Cthangover.MyCodeMod
{
    public class MyMod : IModInitializer
    {
        public void OnModLoaded(string modId) { }

        public void OnModResourcesReady()
        {

            GameLogger.Log("MY_MOD", "My mod loaded!", LogLevel.Message);
        }

    }
}

The IMod interface is the mandatory entry point for any C# mod. The Initialize method is called when the mod loads.

Use GameLogger.Log(...) instead of GD.Print(...) if you want to work with logs.

Step 4: Menu settings — IModSettings

Add to MyModSettings.cs:

using System.Collections.Generic;
using Cthangover.Core.Mods;
using Cthangover.Core.Settings;

public class MyModSettings : IModSettings
{
    private float _volume = 1.0f;
    private bool _enabled = true;

    public IReadOnlyList<ModSettingDefinition> GetDefinitions()
    {
        return new List<ModSettingDefinition>
        {
            new()
            {
                Key = "effect_volume",
                Name = "mymod/effect_volume",
                Type = SettingType.Slider,
                DefaultValue = "1.0",
                Min = 0f,
                Max = 2f,
                Step = 0.1f
            },
            new()
            {
                Key = "enable_mod",
                Name = "mymod/enable_mod",
                Type = SettingType.Bool,
                DefaultValue = "true"
            }
        };
    }

    public void WriteValues(DataBlob blob)
    {
        blob.SetFloat("effect_volume", _volume);
        blob.SetBool("enable_mod", _enabled);
    }

    public void ReadValues(DataBlob blob)
    {
        _volume = blob.GetFloat("effect_volume", 1.0f);
        _enabled = blob.GetBool("enable_mod", true);
    }
}

After the mod loads, go to "Settings → Mod Settings" — your mod appears with a volume slider and a toggle.

Step 5: Custom DSL action — IScenarioAction

Let's add a new my_effect action, usable in .scenario files. Create MyEffectAction.cs:

using Cthangover.Core.Scenarios;
using Cthangover.Core.Actions;
using Cthangover.Core.Utils;

public class MyEffectAction : IScenarioAction
{
    public string Name => "my_effect";

    public void Run(IActionContext context)
    {
        GameLogger.Log("MY_MOD", "New action executed!", LogLevel.Message);
    }
}

Now in any .scenario file you can write:

action my_effect

The engine finds your class via reflection and calls Execute.

Step 6: Localization

mods/quickstart_programmer/locale/en.properties:

mymod/effect_volume = Effect volume
mymod/enable_mod = Enable mod

Step 7: Check it

Start the game:

  1. Open the settings menu → "Mod Settings" tab → your mod with a slider and checkbox.
  2. Write a test .scenario with the action my_effect command.
  3. The game logs show [MY_MOD] New action executed!.
